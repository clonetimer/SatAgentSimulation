# 持续卫星仿真（Continuous Satellite Simulation）

## 适用范围与实施状态

在 V15 原有软实时交互会话上增加 opt-in 的 `continuous: true`。
当前只对 `whole_spacecraft.unified_native.v1` 启用；原有批处理模式、有限时长会话和分系统独立调试保持不变。
这是基于 **同一个 Basilisk 实例的连续状态推进**，不是 CSV/遥测循环回放，也不是硬实时/HIL。

持续模式不会因为 `simulation.duration_s`、`max_sim_time_s`、`max_wall_time_s` 或 `idle_timeout_s` 达到原先的上限而结束；
只有明确 `stop`/`abort`、仿真异常、服务关闭或底层物理/时间表示限制才能终止。
`simulation.duration_s` 仍用于初始模型/热控配置（必须正数），**不是持续模式的结束时刻**。
现实计算机不可能保证物理意义上的无期限可靠运行；连续服务仍须进行长稳测试和重启恢复设计。

## 使用方法

1. 安装与仓库要求匹配的 Basilisk、FastAPI 等依赖。
2. 设置环境变量 `SAT_SIM_INTERACTIVE_ENABLED=1` 并按 `README.md` 启动。
3. 在 Web 工作台「实时会话」中选择「整星」并勾选「持续运行（手动停止）」。
4. 选择仿真推进量子、1× 墙钟节拍后创建并启动会话。
5. 通过遥控面板发送已注册命令；在遥测面板或 WebSocket 中订阅已批准的流。
6. 如需归档，发送 `stop`；如需强制放弃，发送 `abort`。

REST 创建请求示意：

```json
{
  "session_id": "satellite-1",
  "capability_id": "whole_spacecraft.unified_native.v1",
  "continuous": true,
  "quantum_s": 0.5,
  "rate": 1.0,
  "paced": true,
  "task_spec": {
    "simulation": {"duration_s": 60, "sample_s": 0.5, "solver": {"step_s": 0.2}},
    "parameters": {"values": {}},
    "outputs": {"telemetry_streams": [
      {"stream_id": "whole.fast", "sample_s": 0.5, "fields": ["orbit.radius_m"]}
    ]}
  }
}
```

控制端点：`POST /interactive/sessions/satellite-1/control`，请求 `{"action":"start"}`、`{"action":"pause"}`、`{"action":"resume"}`、`{"action":"stop"}` 等。
遥控端点：`POST /interactive/sessions/satellite-1/commands`。
遥测端点：`WS /interactive/sessions/satellite-1/telemetry`。
遥控需要 `session_revision` 和授权角色，严格遵循 `configs/interactive/realtime_capability_matrix.json`。

## 工程边界与后续验收

- 持续模式保持相同 Basilisk 状态，不按预先生成的数据集循环播放。
- 运行时记录器分段清空，连续执行的停止时间只保留末次值；软实时漂移历史保留最近 4096 个采样，但总计数与最大漂移仍保留。
- 遥测总线使用有限环形缓冲，慢消费者会收到 GAP；持久工作区仍连续写盘，**当前没有按日轮转/限额策略**。
- 持续模式的 ACK 和会话事件只保留最近 4096 条内存缓存，序号仍单调增长；完整 ACK/事件继续写入哈希链日志。指定 command_id 的 ACK 查询在有工作区时会遍历日志读取完整历史，未指定 command_id 时返回内存窗口。
- 持续模式的命令 ID 幂等索引保存在 SQLite `command_ids.sqlite`，不会通过淘汰老 ID 来允许重复执行；无显式工作区时使用临时磁盘索引，会话退出即销毁。
- `finalize_telemetry()` 以流式方式校验哈希链、分流写出 JSONL 与计算 SHA-256，归档阶段不再把所有遥测帧保留在 Python 内存中；原有 manifest v1 保持兼容。
- 当前 **尚未完成** 原始遥测日志按日轮转/配额与 Run Bundle 封存全过程流式化：`seal_interactive_workspace()` 仍会完整载入历史 trace。真正 7×24 服务需继续拆分封存与按段归档，防止停止后内存或磁盘耗尽。
- 服务进程重启不等于恢复完整 Basilisk 状态；目前是命令重放/工作区校验方向，完整检查点恢复尚未实现。
- 尚不能以短测试声明 24 小时、7 天或 30 天无故障运行。

推荐测试：
```bash
pytest -q tests/interactive/test_continuous_session.py
pytest -q tests/interactive/test_unified_segmented_execution.py tests/interactive/test_interactive_api.py
python scripts/run_interactive_performance_benchmark.py --profile formal
```

验收应覆盖遥控闭环、连续遥测、Basilisk 跨初始时长、数值等价、进程资源曲线、断线续读，以及 24 小时真实墙钟稳定性。

## 停止与封存状态

- `SessionSnapshot.state=COMPLETED` 表示物理仿真正常结束，不自动表示证据已验证封存。
- `archive_status` 在工作区存在时从 `NOT_READY` 转为 `SEALING`，成功后为 `SEALED`，异常则为 `FAILED` 并给出 `archive_error`；`ABORTED` 等无需封存的结束状态标为 `NOT_APPLICABLE`。
- 实时会话界面独立显示归档状态，避免运行完成但 Run Bundle 不存在的误判。长期运行的分段封存及磁盘配额仍是后续工作。

## 长时间戳加速回归

GitHub 原生测试除了短时 180 s 场景，还包含 3600 s **仿真时间**的加速运行，量子 0.5 s，覆盖连续状态推进、动态遥控、原生采样、工作区哈希链及终态封存；依然不等于真实墙钟 3600 s。测试命令：

```bash
SAT_SIM_CONTINUOUS_SOAK_TARGET_S=3600 pytest -q -s tests/interactive/test_continuous_soak.py
```

24 h 真实墙钟及项目专用 `bsk==2.11.0+satfix1` 的长期门仍需独立验收。

## 内存中的遥测环形缓存

- 持续整星的 `runtime.trace` 包含大量原生模型字段，不开放给普通 API 客户端；该内部流仅缓存最近 **256 帧**供诊断，其完整记录仍由工作区 `telemetry.jsonl` 哈希链落盘。
- 白名单流（如 `whole.fast`、`adcs.fast`）依旧按 `telemetry_buffer_frames` 的容量限制保存最近数据，WebSocket 断线续读和 GAP 语义保持不变。
- 这降低的是 **内存回放缓存** 的成本，不构成物理运行内存泄漏已经排除的证明；还需比较不同仿真时长的进程 RSS 与 Basilisk 内部对象规模。

## 连续遥测存储容量保护

- `telemetry_log_max_bytes` 默认 `0`（不限制单会话原始 `telemetry.jsonl` 的字节数）；设置正整数后，每次实际写盘前精确检查预计字节数，超限抛出 `TELEMETRY_LOG_BUDGET_EXCEEDED`。这是 **主日志预算**，不是对工作区全部文件的配额。
- `telemetry_min_free_disk_bytes` 默认 67108864（64 MiB）；持续模式每 128 个遥测帧检查一次工作区所属磁盘的剩余空间，低于预留量抛出 `TELEMETRY_DISK_RESERVE_EXHAUSTED`。可以设为 `0` 关闭此保护，但不建议生产环境关闭。
- 两项防护只对持续会话生效；故障会终止会话，并通过 `SessionSnapshot.terminal_error` 显示原因。先前完成写盘的证据仍按原哈希链保存，不会自动删旧数据或循环覆盖。
- 这不能替代按段轮转、备份、日志压缩、异地存储或进程状态恢复；归档仍可能额外占用与原始遥测数据相近甚至更多的磁盘空间。

## 持续会话的流式 Run Bundle 封存

- 持续会话与有限时长会话使用不同的封存执行路径，生成的 Run Bundle v1 文件结构及 `semantic_trace_sha256` 保持兼容。
- 持续会话的 `runtime.trace` 逐条读入和计算 SHA-256，`semantic_trace.json` 逐条流式写出，不再构建全量 Python `list[dict]`。完整遥测原始哈希链仍由工作区保存。
- HF-8 工程物理门禁采用流式统计：保持燃料单调性、指向误差首/末/极小值以及逐点物理边界检查；为避免无上限内存积累，物理异常详情达到 2048 条时拒绝封存（`CONTINUOUS_PHYSICAL_ISSUE_LIMIT_EXCEEDED`）。该上限不代表额外的物理真实性认证。
- 遥控效果时间窗按时间顺序扫描遥测，持有的数据规模与已确认的遥控命令数量成正比，而不与遥测总帧数成正比。
- Run Bundle 文件 SHA-256 改为 1 MiB 分块计算。**目前仍会完整加载遥控指令事件以生成效果窗口**；超长会话还需要分段归档、分段封存和完整遥控事件的流式索引设计。
- 该改造不意味着已经实现 Basilisk 物理状态的 checkpoint/restart；重启后的严格物理状态连续性仍未验收。

## 封存的原子发布与失败处理

- 持续会话先在工作区的 `.run_bundle.pending/` 生成语义轨迹、校验结果与 Run Bundle 元数据。只有在完整生成并通过文件哈希验证后，才将其重命名为正式 `run_bundle/`。
- 如果封存过程发生异常，**正式 `run_bundle/` 不会出现未验证的半成品**；未完成的暂存目录原样保留供检查。再次封存时若发现遗留暂存目录，明确报错 `INTERACTIVE_PARTIAL_STAGING_EXISTS`，不会覆盖证据或自动删除。
- 当前暂无自动修复失败暂存目录的能力，检查并恢复前不得将 `archive_status=FAILED` 认定为归档成功。该防护不是操作系统崩溃后已落盘文件必然持久化的保证，生产部署仍需考虑文件系统同步策略。

## 连续遥测原始日志分段轮转

- `telemetry_segment_max_bytes` 默认 67108864（64 MiB），仅持续会话生效；`0` 可关闭轮转。单帧超过分段容量会明确失败（`TELEMETRY_FRAME_EXCEEDS_SEGMENT_CAP`），不会截断帧内容。
- 达到阈值时，将当前 `telemetry.jsonl` 原子重命名为 `telemetry_segments/segment-00000001.jsonl` 等已关闭分段，新的 `telemetry.jsonl` 继续接收后续遥测；已关闭分段的 SHA-256 与字节数记录在 `telemetry_segments/index.json` 中。全局遥测事件序号和 `previous_hash` 不会因分段而重置。
- 工作区的完整性检查按编号检索分段和活动文件，逐段校验内容 SHA-256、跨段哈希链与连续序号；索引缺失、分段缺失或篡改时，拒绝验收。异常轮转遗留未登记分段时要求人工处理，不自动删除或跳过。
- 停止后的 `telemetry_manifest.json` 记录逻辑上完整拼接数据流的 SHA-256 与来源分段信息；流式 Run Bundle 封存会把已关闭分段及活动文件拼接成兼容旧版的 `interactive/telemetry.jsonl`。
- `telemetry_log_max_bytes` 对本会话全部已关闭分段与活动日志的合计字节数生效。**分段轮转并不释放磁盘空间**，不是无限存储，也不取代总量配额与离线归档。当前仍需完成真正的分段压缩/外部归档与保留期清理机制，且不能无验证地删除旧段。

## 分段轮转的恢复边界与验收记录

- 已关闭的分段有编号、文件 SHA-256 和字节数登记；中途异常导致“文件已经重命名而索引尚未提交”时，工作区会拒绝完整性验证，不会自动删除或跳过该分段。
- 停止时的 Run Bundle 内保留向下兼容的完整逻辑 `interactive/telemetry.jsonl`，其哈希基于所有分段与活动文件顺序拼接计算；原始工作区保存分段、索引和活动文件。重新打开工作区时先校验整个分段集合和全局哈希链，再继续写入。
- `telemetry_log_max_bytes` 是所有已关闭段加活动日志的**总字节**上限；轮转不会让这一上限重置。超过上限拒绝新帧，而不会丢弃旧帧。
- 这一步是分段管理，不是磁盘清理或压缩。生产场景仍需基于端到端证据闭环实现离线导出、分段清理策略、磁盘预警，以及 Basilisk 全物理状态恢复。

## 离线、可验证的关闭分段 gzip 压缩

持续会话停止并完成终态持久化后，可以选择压缩其已关闭的 JSONL 分段；**运行中的卫星不允许使用此运维入口执行压缩**。所有原始哈希链均以解压后的原始字节为准，保持全局遥测序号、`previous_hash`、Run Bundle v1 和数据完整性语义不变。

```bash
PYTHONPATH=src:. python scripts/archive_continuous_telemetry.py --workspace runs/interactive/<session_id>
# 可选：每次仅处理不超过 3 个已关闭分段
PYTHONPATH=src:. python scripts/archive_continuous_telemetry.py --workspace runs/interactive/<session_id> --max-segments 3
# 仅在一次压缩意外中断、出现可确认的明文和压缩双份文件时显式使用
PYTHONPATH=src:. python scripts/archive_continuous_telemetry.py --workspace runs/interactive/<session_id> --repair-interrupted-compression
```

- 关闭分段可同时存在旧版 `segment-NNNNNNNN.jsonl` 和新版 `segment-NNNNNNNN.jsonl.gz` 两种格式。压缩格式在原索引中增加压缩文件 SHA-256 和字节数，以及解压原文的 `raw_sha256`、`raw_bytes`。
- 每个旧分段首先压缩到暂存文件，检验解压字节与原文完全一致；再发布压缩文件、提交新索引、移除冗余明文。任何时刻发现未登记或重复分段都会拒绝完整性检查，不会静默跳过遥测数据。
- 仅当 **双份文件均经独立哈希证明为同一数据** 时，显式恢复命令才会按索引指向移除冗余副本；分段损坏、丢失、跨段断链无法通过该命令修复。
- `telemetry_log_max_bytes` 仍按 **解压后全部逻辑数据** 计算，从而不会因为压缩而重置证据保留配额。实际磁盘使用可下降，但压缩不会自动上传远端，也不会释放尚未封存的其他文件。
- 已密封 Run Bundle 是独立的不可变证据，压缩工作区分段不会重写其中的 `interactive/telemetry.jsonl`。工作区的 `telemetry_manifest.json` 来源分段字段描述封存时的状态，后续压缩不能反向改动已密封清单。
- 该压缩仅限离线会话，与实际长时在线无故障运行、遥测异地存储、完整 Basilisk 物理状态 checkpoint/restart 是不同验收项目。

归档运维命令增加了额外的安全前置检查：仅允许 `COMPLETED` 且已经存在经校验通过的 `run_bundle/SEALED.json` 的工作区执行普通压缩。仅有终态状态事件、但封存尚未完成的会话，或证据校验不通过的工作区均会拒绝压缩；显式中断修复仍是独立的人工操作入口。


## 异常退出后可验证的恢复交接（仅证据恢复，不是原生物理续跑）

卫星整星 Basilisk 对象图当前没有统一、可验证的完整状态序列化与恢复机制。进程异常退出后，系统**不会**把最后一帧遥测反写为 Basilisk 内部状态，也不会从原仿真时间戳直接恢复运行。

服务再次启动、检查到未正常终止的持续会话时：

1. 按原有日志及跨压缩分段遥测哈希链验证工作区；验证失败则拒绝恢复交接，不修改破损证据。
2. 在状态事件链中记录 `INTERRUPTED / PROCESS_RESTART`，保留此前的状态、遥控 ACK 和完整遥测证据。
3. 生成 `recovery_handoff.json`：记载来源文件 SHA-256、跨分段逻辑遥测 SHA-256、最后已落盘遥测的仿真时刻、最后 `runtime.trace` 时刻以及状态/遥控/遥测事件数量。
4. 为避免“心跳事件时刻”和“真实最后观测时刻”被混淆，两个时间字段独立记录。即使遥测比心跳更新，也**不能**由此证明全部隐藏物理状态已经存盘。
5. 交接文件具有内容摘要，并允许后续重新对照原始证据验真。原数据被修改、交接记录被篡改均会拒绝使用。

```bash
# 验证此前重启生成的交接记录，严格只读
PYTHONPATH=src:. python scripts/inspect_continuous_recovery.py --workspace runs/interactive/<session_id>

# 仅当工作区已明确标记 PROCESS_RESTART、历史证据验证有效且确实缺少交接文件时，
# 显式生成缺失交接，不能覆盖已有交接或绕过损坏数据
PYTHONPATH=src:. python scripts/inspect_continuous_recovery.py --workspace runs/interactive/<session_id> --create-missing
```

### 不能直接恢复的原生状态

| 层次 | 典型尚未保证完整恢复的状态 |
|---|---|
| 动力学积分器 | 内部积分状态及轨道位置、速度、姿态、角速度的精确续算边界 |
| ADCS 执行器与控制器 | 反作用轮实际内部状态、控制积分器、指向目标、故障注入状态 |
| EPS / 热控 | 电池内部荷电状态、功率平衡动态、热节点历史/积分内部量 |
| 通信 / 数据 | 缓存、下行队列、已生成载荷数据与模型内部中间状态 |
| 调度与交互 | 仿真事件触发器、已排队遥控、命令去重状态、随机过程状态 |

**验收原则：** 只有所有需要的 Basilisk 原生模块与项目模块均能导出/导入状态，并在相同命令、相同时间推进条件下证明“中断恢复后”和“未中断基准”的物理与遥测一致，才可以将 `resume_supported` 改为 `true`。

当前交接仅允许从**新 session_id、初始条件**创建一个新的独立仿真轮次（new epoch）。新轮次不得标为无损恢复、不得复用旧轮次的任务/结果身份，也不得自动重放具有物理副作用的遥控指令。24 小时真实墙钟稳定性和 `bsk==2.11.0+satfix1` 环境复验仍未完成。


## 原生 Basilisk checkpoint 能力覆盖审计（只读实验接口）

已增加 `UnifiedPersistentRuntime.audit_native_checkpoint_coverage()`，仅在**已推进的持续仿真**上可调用。审计请求会发送到原来持有 Basilisk 实例的工作线程，在模型停止于确定的仿真时刻执行只读观测，**不新建模拟器、不清空状态、不修改仿真时间**。

该报告标识 `sat-native-checkpoint-coverage.v1`，记录原生工作线程标识、当前仿真时刻、航天器位置/速度/MRP/角速度，以及可读取的 ADCS 指向目标、控制器增益、电池状态和数据存储量；不可读取的字段列出实际异常，而不从此前遥测文件推断。

与可观测量独立，覆盖审计明确登记 12 类完整恢复必需的状态所有者，包括调度器/积分器、航天器动力学、反作用轮、ADCS 控制器记忆、噪声随机状态、EPS、热控、通信数据、推进、故障事件与未执行遥控。**目前没有任何一类完成“原生导出 + 原生导入 + 不中断对照数值等价”闭环**，因此报告不可更改地设为 `resume_supported=false`、`native_checkpoint_complete=false`。测试还检验报告哈希及企图将其伪装成可恢复的篡改行为。

该接口用于后续逐模块开发和审查，不是可自动执行的恢复按钮，也不取代前述 `recovery_handoff.json`。进入下一阶段，应优先测试动力学集成状态与反作用轮恢复接口，随后扩展 EPS/热控/通信数据/调度和指令队列；只有对全部必须状态证明恢复一致性，才能取消 fail-closed 限制。


### 操作者 API：实时查看原生 checkpoint 覆盖率

持续会话已经推进、且**暂停**之后，具有 operator、fault_operator 或 admin 身份的客户端可以调用：

```http
GET /interactive/sessions/{session_id}/checkpoint/coverage
```

该端点通过会话工作线程转发审计请求，由**同一个真实 Basilisk 实例所在的原生工作线程**读取状态；拒绝有限时长会话、未推进会话、运行中会话和 viewer 权限。读取不改变卫星仿真时间，也不会修改任务配置。返回的是 `sat-native-checkpoint-coverage.v1` 能力审计证据，`resume_supported` 仍为 `false`。它不保存可加载的物理 checkpoint，不能用于执行重启续跑。


## Basilisk 原生 StateData 动力学/反作用轮状态导出与原地回填试验

已利用 `bsk 2.11.0` 的真实 SWIG 接口验证 `spacecraft.dynManager.getStateObject(...).getState()/setState()`：
`hubPosition`、`hubVelocity`、`hubSigma`、`hubOmega` 和 `reactionWheelOmegas` 都能在已经初始化的 Basilisk 实例上取得真实积分状态；这些不等于 `scStateOutMsg` 的观测遥测。新增 `native_state_pilot.py` 对五组状态实施维度/有限性校验、固定格式 SHA-256，并提供仅用于内部测试的 `restore_state_subset_in_place()`，不对 API 或生产 TC 开放写入接口。

独立测试采用两个具有相同模型配置的原生 Basilisk 实例，先推进到相同的中间时刻；随后故意扰动其中一个实例的位置状态，在同一个已暂停的实例中写回先前记录的五组状态，再继续推进，并与未扰动基准作数值比较。另测试反作用轮数目不符、哈希被篡改时应拒绝写入。

`checkpoint/coverage` 报告现在会附带实际获取的 `native_state_subset_pilot`；若获取失败，列出错误而不伪造导出。该试验只证明**局部状态原地读写及指定隔离模型的后续数值一致性**，绝不证明杀死原进程、新建 Basilisk 对象之后的完整物理状态与时间调度恢复。报告仍然强制 `resume_supported=false`。


## 跨 Python 进程的全新 Basilisk 模型状态重基准试验

为了进一步区别“原地回填”与“重新创建原生实例”，新增 `tests/interactive/test_native_state_pilot.py` 跨操作系统进程回归：

1. 在源 Python 进程中创建真实 Basilisk 的航天器动力学、地球中心引力和三只反作用轮模型，将其推进到中间时刻 `t=2.0 s`。
2. 从 Basilisk C++ `StateData` 注册表读取并带 SHA-256 存储 `hubPosition`、`hubVelocity`、`hubSigma`、`hubOmega` 和 `reactionWheelOmegas` 五组状态。
3. 源进程继续正常推进到 `t=5.0 s`，生成**不中断基准**。
4. 启动新的独立 Python 子进程，由它重新创建相同的 Basilisk 动力学模型；其调度时钟由 `0` 开始，向新实例的 `StateData` 写入第 2 步的五组状态，再推进相对时间 `3.0 s`。
5. 对五组最终状态进行严格数值对照，检验子进程 PID 不同、时间戳重基准确实发生，以及任何报告均未宣称整星 `resume_supported=true`。

**验收结果：** 在上述具有地球引力但没有外部定时事件、随机噪声、FSW/EPS/热控/通信数据内部状态的**自治试验图**中，五组最终状态与未中断基准一致。实验还拒绝不在允许清单内的模型 profile，防止将整星故障时序误用为自治轨迹试验。

**严格能力边界：** 这项测试不是整星跨进程状态续跑。新进程的 Basilisk 时钟为零，而原进程是绝对时间 `t=2.0 s` 之后继续运行；仅由于这里的动力学为自治系统，时间重基准才可用于数值比较。任何依赖绝对任务时钟的 FSW、故障事件、温度/电池/数据模型、随机过程和待执行遥控都不能直接据此恢复。项目的 `native_checkpoint_complete=false`、`resume_supported=false` 保持不变。

下一阶段重点是调查并验证 Basilisk 调度器/积分器的真实时间恢复能力，配合分系统逐项状态导出导入；必须实现带时间触发故障和遥控事件的**完整整星中断/恢复轨迹对照**，才能宣称生产可用的 checkpoint/restart。


## 时序恢复实验：绝对事件时刻到新进程时间轴的严格映射

Basilisk 新建仿真实例的调度时钟仍从 0 起算，之前的局部状态移植实验不能自动恢复故障时刻、遥控时序、周期积分器相位或模块内部的历史量。

新增 **仅用于隔离实验图** 的 `native_time_rebase_pilot.py`，只接受固定步长、网格对齐且严格递增的**未来外加力矩事件**，将原进程事件的绝对时刻换算成新进程的相对时刻。事件处于检查点之前或恰好落在检查点、跨步长边界、重复、逆序、非有限值及未经允许的整星模型都必须拒绝；这些情况不能仅凭一份动力学状态文件判断历史副作用是否已执行。

新增跨进程原生对照试验：地球中心引力 + 三反作用轮 + Basilisk `extForceTorque`。源模型在 `t=2 s` 获取状态，于绝对时刻 `t=3 s` 加力矩、`t=4 s` 撤力矩，并推进到 `t=5 s`；新进程从相对时刻 0 载入状态，将事件映射至相对时刻 1/2 s，然后推进到相对时刻 3 s。试验同时计算**不映射绝对时刻**的错误恢复路径，用最终角速度差异暴露时序丢失。该试验必须由原生 Basilisk CI 实际验证，不能依靠模拟数据代替。

即使上述试验通过，也仅能证明某一固定步长、显式外部输入的模型中“时序映射 + 局部状态”可以复现结果；它**不等于**恢复原生调度时钟或积分器内部相位，更未覆盖卫星 FSW、EPS、热控、数据缓存、任务模式、故障事件与队列中的遥控。不得将其用作公开的整星 checkpoint/restore 接口，`resume_supported=false` 继续保持。
