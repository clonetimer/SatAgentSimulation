# 持续卫星仿真（Continuous Satellite Simulation）

## 适用范围与实施状态

在 V15 原有软实时交互会话上增加 opt-in 的 `continuous: true`。
当前只对 `whole_spacecraft.unified_native.v1` 启用；原有批处理模式、有限时长会话和分系统独立调试保持不变。
这是基于 **同一个 Basilisk 实例的连续状态推进**，不是 CSV/遥测循环回放，也不是硬实时/HIL。

持续模式不会因为 `simulation.duration_s`、`max_sim_time_s`、`max_wall_time_s` 或 `idle_timeout_s` 达到原先的上限而结束；
只有明确 `stop`/`abort`、仿真异常、服务关闭或底层物理/时间表示限制才能终止。
`simulation.duration_s` 仍用于初始模型/热控配置（必须正数），**不是持续模式的结束时刻**。
现实计算机不可能保证物理意义上的无期限可靠运行；连续服务仍须进行长稳测试和重启恢复设计。

## 使用方法

1. 安装与仓库要求匹配的 Basilisk、FastAPI 等依赖。
2. 设置环境变量 `SAT_SIM_INTERACTIVE_ENABLED=1` 并按 `README.md` 启动。
3. 在 Web 工作台「实时会话」中选择「整星」并勾选「持续运行（手动停止）」。
4. 选择仿真推进量子、1× 墙钟节拍后创建并启动会话。
5. 通过遥控面板发送已注册命令；在遥测面板或 WebSocket 中订阅已批准的流。
6. 如需归档，发送 `stop`；如需强制放弃，发送 `abort`。

REST 创建请求示意：

```json
{
  "session_id": "satellite-1",
  "capability_id": "whole_spacecraft.unified_native.v1",
  "continuous": true,
  "quantum_s": 0.5,
  "rate": 1.0,
  "paced": true,
  "task_spec": {
    "simulation": {"duration_s": 60, "sample_s": 0.5, "solver": {"step_s": 0.2}},
    "parameters": {"values": {}},
    "outputs": {"telemetry_streams": [
      {"stream_id": "whole.fast", "sample_s": 0.5, "fields": ["orbit.radius_m"]}
    ]}
  }
}
```

控制端点：`POST /interactive/sessions/satellite-1/control`，请求 `{"action":"start"}`、`{"action":"pause"}`、`{"action":"resume"}`、`{"action":"stop"}` 等。
遥控端点：`POST /interactive/sessions/satellite-1/commands`。
遥测端点：`WS /interactive/sessions/satellite-1/telemetry`。
遥控需要 `session_revision` 和授权角色，严格遵循 `configs/interactive/realtime_capability_matrix.json`。

## 工程边界与后续验收

- 持续模式保持相同 Basilisk 状态，不按预先生成的数据集循环播放。
- 运行时记录器分段清空，连续执行的停止时间只保留末次值；软实时漂移历史保留最近 4096 个采样，但总计数与最大漂移仍保留。
- 遥测总线使用有限环形缓冲，慢消费者会收到 GAP；持久工作区仍连续写盘，**当前没有按日轮转/限额策略**。
- 持续模式的 ACK 和会话事件只保留最近 4096 条内存缓存，序号仍单调增长；完整 ACK/事件继续写入哈希链日志。指定 command_id 的 ACK 查询在有工作区时会遍历日志读取完整历史，未指定 command_id 时返回内存窗口。
- 持续模式的命令 ID 幂等索引保存在 SQLite `command_ids.sqlite`，不会通过淘汰老 ID 来允许重复执行；无显式工作区时使用临时磁盘索引，会话退出即销毁。
- `finalize_telemetry()` 以流式方式校验哈希链、分流写出 JSONL 与计算 SHA-256，归档阶段不再把所有遥测帧保留在 Python 内存中；原有 manifest v1 保持兼容。
- 当前 **尚未完成** 原始遥测日志按日轮转/配额与 Run Bundle 封存全过程流式化：`seal_interactive_workspace()` 仍会完整载入历史 trace。真正 7×24 服务需继续拆分封存与按段归档，防止停止后内存或磁盘耗尽。
- 服务进程重启不等于恢复完整 Basilisk 状态；目前是命令重放/工作区校验方向，完整检查点恢复尚未实现。
- 尚不能以短测试声明 24 小时、7 天或 30 天无故障运行。

推荐测试：
```bash
pytest -q tests/interactive/test_continuous_session.py
pytest -q tests/interactive/test_unified_segmented_execution.py tests/interactive/test_interactive_api.py
python scripts/run_interactive_performance_benchmark.py --profile formal
```

验收应覆盖遥控闭环、连续遥测、Basilisk 跨初始时长、数值等价、进程资源曲线、断线续读，以及 24 小时真实墙钟稳定性。

## 停止与封存状态

- `SessionSnapshot.state=COMPLETED` 表示物理仿真正常结束，不自动表示证据已验证封存。
- `archive_status` 在工作区存在时从 `NOT_READY` 转为 `SEALING`，成功后为 `SEALED`，异常则为 `FAILED` 并给出 `archive_error`；`ABORTED` 等无需封存的结束状态标为 `NOT_APPLICABLE`。
- 实时会话界面独立显示归档状态，避免运行完成但 Run Bundle 不存在的误判。长期运行的分段封存及磁盘配额仍是后续工作。

## 长时间戳加速回归

GitHub 原生测试除了短时 180 s 场景，还包含 3600 s **仿真时间**的加速运行，量子 0.5 s，覆盖连续状态推进、动态遥控、原生采样、工作区哈希链及终态封存；依然不等于真实墙钟 3600 s。测试命令：

```bash
SAT_SIM_CONTINUOUS_SOAK_TARGET_S=3600 pytest -q -s tests/interactive/test_continuous_soak.py
```

24 h 真实墙钟及项目专用 `bsk==2.11.0+satfix1` 的长期门仍需独立验收。

## 内存中的遥测环形缓存

- 持续整星的 `runtime.trace` 包含大量原生模型字段，不开放给普通 API 客户端；该内部流仅缓存最近 **256 帧**供诊断，其完整记录仍由工作区 `telemetry.jsonl` 哈希链落盘。
- 白名单流（如 `whole.fast`、`adcs.fast`）依旧按 `telemetry_buffer_frames` 的容量限制保存最近数据，WebSocket 断线续读和 GAP 语义保持不变。
- 这降低的是 **内存回放缓存** 的成本，不构成物理运行内存泄漏已经排除的证明；还需比较不同仿真时长的进程 RSS 与 Basilisk 内部对象规模。

## 连续遥测存储容量保护

- `telemetry_log_max_bytes` 默认 `0`（不限制单会话原始 `telemetry.jsonl` 的字节数）；设置正整数后，每次实际写盘前精确检查预计字节数，超限抛出 `TELEMETRY_LOG_BUDGET_EXCEEDED`。这是 **主日志预算**，不是对工作区全部文件的配额。
- `telemetry_min_free_disk_bytes` 默认 67108864（64 MiB）；持续模式每 128 个遥测帧检查一次工作区所属磁盘的剩余空间，低于预留量抛出 `TELEMETRY_DISK_RESERVE_EXHAUSTED`。可以设为 `0` 关闭此保护，但不建议生产环境关闭。
- 两项防护只对持续会话生效；故障会终止会话，并通过 `SessionSnapshot.terminal_error` 显示原因。先前完成写盘的证据仍按原哈希链保存，不会自动删旧数据或循环覆盖。
- 这不能替代按段轮转、备份、日志压缩、异地存储或进程状态恢复；归档仍可能额外占用与原始遥测数据相近甚至更多的磁盘空间。

## 持续会话的流式 Run Bundle 封存

- 持续会话与有限时长会话使用不同的封存执行路径，生成的 Run Bundle v1 文件结构及 `semantic_trace_sha256` 保持兼容。
- 持续会话的 `runtime.trace` 逐条读入和计算 SHA-256，`semantic_trace.json` 逐条流式写出，不再构建全量 Python `list[dict]`。完整遥测原始哈希链仍由工作区保存。
- HF-8 工程物理门禁采用流式统计：保持燃料单调性、指向误差首/末/极小值以及逐点物理边界检查；为避免无上限内存积累，物理异常详情达到 2048 条时拒绝封存（`CONTINUOUS_PHYSICAL_ISSUE_LIMIT_EXCEEDED`）。该上限不代表额外的物理真实性认证。
- 遥控效果时间窗按时间顺序扫描遥测，持有的数据规模与已确认的遥控命令数量成正比，而不与遥测总帧数成正比。
- Run Bundle 文件 SHA-256 改为 1 MiB 分块计算。**目前仍会完整加载遥控指令事件以生成效果窗口**；超长会话还需要分段归档、分段封存和完整遥控事件的流式索引设计。
- 该改造不意味着已经实现 Basilisk 物理状态的 checkpoint/restart；重启后的严格物理状态连续性仍未验收。

## 封存的原子发布与失败处理

- 持续会话先在工作区的 `.run_bundle.pending/` 生成语义轨迹、校验结果与 Run Bundle 元数据。只有在完整生成并通过文件哈希验证后，才将其重命名为正式 `run_bundle/`。
- 如果封存过程发生异常，**正式 `run_bundle/` 不会出现未验证的半成品**；未完成的暂存目录原样保留供检查。再次封存时若发现遗留暂存目录，明确报错 `INTERACTIVE_PARTIAL_STAGING_EXISTS`，不会覆盖证据或自动删除。
- 当前暂无自动修复失败暂存目录的能力，检查并恢复前不得将 `archive_status=FAILED` 认定为归档成功。该防护不是操作系统崩溃后已落盘文件必然持久化的保证，生产部署仍需考虑文件系统同步策略。

## 连续遥测原始日志分段轮转

- `telemetry_segment_max_bytes` 默认 67108864（64 MiB），仅持续会话生效；`0` 可关闭轮转。单帧超过分段容量会明确失败（`TELEMETRY_FRAME_EXCEEDS_SEGMENT_CAP`），不会截断帧内容。
- 达到阈值时，将当前 `telemetry.jsonl` 原子重命名为 `telemetry_segments/segment-00000001.jsonl` 等已关闭分段，新的 `telemetry.jsonl` 继续接收后续遥测；已关闭分段的 SHA-256 与字节数记录在 `telemetry_segments/index.json` 中。全局遥测事件序号和 `previous_hash` 不会因分段而重置。
- 工作区的完整性检查按编号检索分段和活动文件，逐段校验内容 SHA-256、跨段哈希链与连续序号；索引缺失、分段缺失或篡改时，拒绝验收。异常轮转遗留未登记分段时要求人工处理，不自动删除或跳过。
- 停止后的 `telemetry_manifest.json` 记录逻辑上完整拼接数据流的 SHA-256 与来源分段信息；流式 Run Bundle 封存会把已关闭分段及活动文件拼接成兼容旧版的 `interactive/telemetry.jsonl`。
- `telemetry_log_max_bytes` 对本会话全部已关闭分段与活动日志的合计字节数生效。**分段轮转并不释放磁盘空间**，不是无限存储，也不取代总量配额与离线归档。当前仍需完成真正的分段压缩/外部归档与保留期清理机制，且不能无验证地删除旧段。

## 分段轮转的恢复边界与验收记录

- 已关闭的分段有编号、文件 SHA-256 和字节数登记；中途异常导致“文件已经重命名而索引尚未提交”时，工作区会拒绝完整性验证，不会自动删除或跳过该分段。
- 停止时的 Run Bundle 内保留向下兼容的完整逻辑 `interactive/telemetry.jsonl`，其哈希基于所有分段与活动文件顺序拼接计算；原始工作区保存分段、索引和活动文件。重新打开工作区时先校验整个分段集合和全局哈希链，再继续写入。
- `telemetry_log_max_bytes` 是所有已关闭段加活动日志的**总字节**上限；轮转不会让这一上限重置。超过上限拒绝新帧，而不会丢弃旧帧。
- 这一步是分段管理，不是磁盘清理或压缩。生产场景仍需基于端到端证据闭环实现离线导出、分段清理策略、磁盘预警，以及 Basilisk 全物理状态恢复。

## 离线、可验证的关闭分段 gzip 压缩

持续会话停止并完成终态持久化后，可以选择压缩其已关闭的 JSONL 分段；**运行中的卫星不允许使用此运维入口执行压缩**。所有原始哈希链均以解压后的原始字节为准，保持全局遥测序号、`previous_hash`、Run Bundle v1 和数据完整性语义不变。

```bash
PYTHONPATH=src:. python scripts/archive_continuous_telemetry.py --workspace runs/interactive/<session_id>
# 可选：每次仅处理不超过 3 个已关闭分段
PYTHONPATH=src:. python scripts/archive_continuous_telemetry.py --workspace runs/interactive/<session_id> --max-segments 3
# 仅在一次压缩意外中断、出现可确认的明文和压缩双份文件时显式使用
PYTHONPATH=src:. python scripts/archive_continuous_telemetry.py --workspace runs/interactive/<session_id> --repair-interrupted-compression
```

- 关闭分段可同时存在旧版 `segment-NNNNNNNN.jsonl` 和新版 `segment-NNNNNNNN.jsonl.gz` 两种格式。压缩格式在原索引中增加压缩文件 SHA-256 和字节数，以及解压原文的 `raw_sha256`、`raw_bytes`。
- 每个旧分段首先压缩到暂存文件，检验解压字节与原文完全一致；再发布压缩文件、提交新索引、移除冗余明文。任何时刻发现未登记或重复分段都会拒绝完整性检查，不会静默跳过遥测数据。
- 仅当 **双份文件均经独立哈希证明为同一数据** 时，显式恢复命令才会按索引指向移除冗余副本；分段损坏、丢失、跨段断链无法通过该命令修复。
- `telemetry_log_max_bytes` 仍按 **解压后全部逻辑数据** 计算，从而不会因为压缩而重置证据保留配额。实际磁盘使用可下降，但压缩不会自动上传远端，也不会释放尚未封存的其他文件。
- 已密封 Run Bundle 是独立的不可变证据，压缩工作区分段不会重写其中的 `interactive/telemetry.jsonl`。工作区的 `telemetry_manifest.json` 来源分段字段描述封存时的状态，后续压缩不能反向改动已密封清单。
- 该压缩仅限离线会话，与实际长时在线无故障运行、遥测异地存储、完整 Basilisk 物理状态 checkpoint/restart 是不同验收项目。

归档运维命令增加了额外的安全前置检查：仅允许 `COMPLETED` 且已经存在经校验通过的 `run_bundle/SEALED.json` 的工作区执行普通压缩。仅有终态状态事件、但封存尚未完成的会话，或证据校验不通过的工作区均会拒绝压缩；显式中断修复仍是独立的人工操作入口。


## 异常退出后可验证的恢复交接（仅证据恢复，不是原生物理续跑）

卫星整星 Basilisk 对象图当前没有统一、可验证的完整状态序列化与恢复机制。进程异常退出后，系统**不会**把最后一帧遥测反写为 Basilisk 内部状态，也不会从原仿真时间戳直接恢复运行。

服务再次启动、检查到未正常终止的持续会话时：

1. 按原有日志及跨压缩分段遥测哈希链验证工作区；验证失败则拒绝恢复交接，不修改破损证据。
2. 在状态事件链中记录 `INTERRUPTED / PROCESS_RESTART`，保留此前的状态、遥控 ACK 和完整遥测证据。
3. 生成 `recovery_handoff.json`：记载来源文件 SHA-256、跨分段逻辑遥测 SHA-256、最后已落盘遥测的仿真时刻、最后 `runtime.trace` 时刻以及状态/遥控/遥测事件数量。
4. 为避免“心跳事件时刻”和“真实最后观测时刻”被混淆，两个时间字段独立记录。即使遥测比心跳更新，也**不能**由此证明全部隐藏物理状态已经存盘。
5. 交接文件具有内容摘要，并允许后续重新对照原始证据验真。原数据被修改、交接记录被篡改均会拒绝使用。

```bash
# 验证此前重启生成的交接记录，严格只读
PYTHONPATH=src:. python scripts/inspect_continuous_recovery.py --workspace runs/interactive/<session_id>

# 仅当工作区已明确标记 PROCESS_RESTART、历史证据验证有效且确实缺少交接文件时，
# 显式生成缺失交接，不能覆盖已有交接或绕过损坏数据
PYTHONPATH=src:. python scripts/inspect_continuous_recovery.py --workspace runs/interactive/<session_id> --create-missing
```

### 不能直接恢复的原生状态

| 层次 | 典型尚未保证完整恢复的状态 |
|---|---|
| 动力学积分器 | 内部积分状态及轨道位置、速度、姿态、角速度的精确续算边界 |
| ADCS 执行器与控制器 | 反作用轮实际内部状态、控制积分器、指向目标、故障注入状态 |
| EPS / 热控 | 电池内部荷电状态、功率平衡动态、热节点历史/积分内部量 |
| 通信 / 数据 | 缓存、下行队列、已生成载荷数据与模型内部中间状态 |
| 调度与交互 | 仿真事件触发器、已排队遥控、命令去重状态、随机过程状态 |

**验收原则：** 只有所有需要的 Basilisk 原生模块与项目模块均能导出/导入状态，并在相同命令、相同时间推进条件下证明“中断恢复后”和“未中断基准”的物理与遥测一致，才可以将 `resume_supported` 改为 `true`。

当前交接仅允许从**新 session_id、初始条件**创建一个新的独立仿真轮次（new epoch）。新轮次不得标为无损恢复、不得复用旧轮次的任务/结果身份，也不得自动重放具有物理副作用的遥控指令。24 小时真实墙钟稳定性和 `bsk==2.11.0+satfix1` 环境复验仍未完成。


## 原生 Basilisk checkpoint 能力覆盖审计（只读实验接口）

已增加 `UnifiedPersistentRuntime.audit_native_checkpoint_coverage()`，仅在**已推进的持续仿真**上可调用。审计请求会发送到原来持有 Basilisk 实例的工作线程，在模型停止于确定的仿真时刻执行只读观测，**不新建模拟器、不清空状态、不修改仿真时间**。

该报告标识 `sat-native-checkpoint-coverage.v1`，记录原生工作线程标识、当前仿真时刻、航天器位置/速度/MRP/角速度，以及可读取的 ADCS 指向目标、控制器增益、电池状态和数据存储量；不可读取的字段列出实际异常，而不从此前遥测文件推断。

## 时序恢复实验：绝对事件时刻到新进程时间轴的严格映射

Basilisk 新建仿真实例的调度时钟仍从 0 起算，之前的局部状态移植实验不能自动恢复故障时刻、遥控时序、周期积分器相位或模块内部的历史量。

新增 **仅用于隔离实验图** 的 `native_time_rebase_pilot.py`，只接受固定步长、网格对齐且严格递增的**未来外加力矩事件**，将原进程事件的绝对时刻换算成新进程的相对时刻。事件处于检查点之前或恰好落在检查点、跨步长边界、重复、逆序、非有限值及未经允许的整星模型都必须拒绝；这些情况不能仅凭一份动力学状态文件判断历史副作用是否已执行。

新增跨进程原生对照试验：地球中心引力 + 三反作用轮 + Basilisk `extForceTorque`。源模型在 `t=2 s` 获取状态，于绝对时刻 `t=3 s` 加力矩、`t=4 s` 撤力矩，并推进到 `t=5 s`；新进程从相对时刻 0 载入状态，将事件映射至相对时刻 1/2 s，然后推进到相对时刻 3 s。试验同时计算**不映射绝对时刻**的错误恢复路径，用最终角速度差异暴露时序丢失。该试验必须由原生 Basilisk CI 实际验证，不能依靠模拟数据代替。

即使上述试验通过，也仅能证明某一固定步长、显式外部输入的模型中“时序映射 + 局部状态”可以复现结果；它**不等于**恢复原生调度时钟或积分器内部相位，更未覆盖卫星 FSW、EPS、热控、数据缓存、任务模式、故障事件与队列中的遥控。不得将其用作公开的整星 checkpoint/restore 接口，`resume_supported=false` 继续保持。


### 原生调度相位的只读证据

`checkpoint/coverage` 报告增加 `native_scheduler_phase`，由持有 Basilisk 实例的原生工作线程直接读取 `sim.TotalSim.CurrentNanos`（当前时间）和 `sim.TotalSim.NextTaskTime`（下一计划执行任务时间），保留纳秒整数及其差值。若读到下一任务时间早于当前时间，审计直接拒绝报告；读取不会设置任一调度字段。

必须注意：**保存这两个计数器不意味着能够恢复调度器。** 进程重建还需要恢复任务开始时刻、优先级、执行次数、事件处理历史、积分器相位、模块隐藏状态与消息时间戳。报告强制设置 `native_clock_restore_proven=false`、`task_queue_restore_proven=false`、`event_queue_restore_proven=false`，并继续保持整星 `resume_supported=false`。

下一步开发需针对 Basilisk 的调度器任务队列与积分器状态，建立 **跨进程、绝对仿真时间连续** 的对照试验。当前带力矩时序的成功案例属于事件时刻映射，而非调度器原位续跑。


## 单任务原生调度器与动力学积分时间的跨进程恢复试验

继上一轮只读 `CurrentNanos`、`NextTaskTime` 及未来事件重基准试验之后，本轮进一步在具有固定 0.2s 任务周期的隔离模型中审查 Basilisk 的可写 C++/SWIG 字段。实际测试发现，仅设置原进程的 `CurrentNanos`、`NextTaskTime`、`process.nextTaskTime`、`task.NextStartTime` 等调度字段及五组 `StateData`，**不能正确恢复轨迹**，因为航天器 `timeBefore`、`timeBeforeNanos`、`timeStep` 仍保留新建实例的零值。

新增 `native_scheduler_pilot.py`：为**仅有一个进程、一个等周期任务，包含地球中心引力、航天器刚体与三反作用轮**的独立实验图记录并严格校验 11 个时间字段（调度器、进程、任务与航天器积分时间），以及整体 SHA-256。只允许在初始化完毕、调度器仍处于 t=0 的**全新隔离实验实例**中原地回填，并在继续计算前比对全部读取结果；不接受重复恢复、网格未对齐、错误步长、不同任务数量、篡改或误标完整整星续跑的记录。

新增跨 Python 进程真实原生对照测试：源实例推进至 `t=2s` 保存五组动力学状态和 11 项时间字段，连续推进至 `t=5s` 为基准；新进程重新创建相同单任务 Basilisk 图，回填后**从原绝对 t=2s 的原生调度时钟继续到 t=5s**，并逐组对照最终动力学状态。同时设置反例：在新进程只回填调度器而故意漏掉航天器 `timeBefore*`，应检出显著的位置偏差。该对照由原生 GitHub Actions 自动执行。

**严格能力边界：** 这是单任务固定步长、单种配置、特定积分器下的受限试验，**不是**完整 Basilisk 积分器/任务队列的通用序列化与恢复机制。没有覆盖多任务优先级、其他动力学 effector 隐藏状态、FSW、电源、热控、通信数据、故障时序、随机状态及排队遥控。恢复代码没有开放到任何生产 HTTP/API 或遥控操作。全整星 `resume_supported=false` 继续保持，须待所有状态所有者的恢复与跨进程数值等价测试通过后才能改变。


## 多任务、不同执行周期的 Basilisk 跨进程恢复验证

前述单任务调度时钟恢复并不足以保证多任务运行。现新增专用实验 `native_multitask_pilot.py`，采用**同一原生进程、两个任务**的 Basilisk 图：航天器刚体＋地球引力＋3 只反作用轮在 0.2 秒动力学任务运行，原生 `simpleNav` 及其遥测记录器在 0.6 秒观测任务运行。

实验在 `t=2.0 s` 保存状态（此时慢任务上一执行时刻为 1.8 秒，下一时刻应为 2.4 秒），独立 Python 进程新建同样的原生图，再从**原绝对 t=2.0s** 恢复到 `t=5.0s`。最终同时比较五组真实动力学 `StateData` 和剩余慢速导航的记录时间戳及位置数据。

**实现中发现的隐藏调度状态：** 同一任务的 `TaskData.NextStartTime` 与 `SysProcess.processTasks[]` 中的 `ModelScheduleEntry.NextTaskStart` 是不同的存储。前者正确并不保证后者正确。只恢复任务数据、不恢复进程调度表，会让慢速任务在 2.2 秒提前执行一次，导致额外遥测帧。Basilisk SWIG 向 Python 暴露的调度表还需要通过**索引写回条目**；仅修改遍历结果可能更改的是对象副本。当前程序因此对原生调度表记录周期、优先级及下一执行时刻，并验证全部写回后的实际读数。

实验包含两条刻意失败的恢复路径：遗漏进程调度表恢复、把慢速任务错移一个周期；两者都会造成与未中断基准不同的导航时间戳，不能以状态矢量一致为由忽略。完整路径在验证过的 0.2/0.6 秒配置中能恢复动力学和后续导航输出。

**测试验收：** GitHub 原生 Basilisk 回归 44 项通过；非 Basilisk 回归 73 项通过（另 1 项环境跳过、1 项筛选排除）；180 秒及 3600 秒加速整星持续运行测试均通过。验证提交 `3f931e69bed4b1c806b9e09627815b926ef2c7fc`，四项 Actions 皆成功。

**适用边界不变：** 当前模块只是单进程、双任务、两个固定周期和已知原生模型组合的内部试验，不是通用 Basilisk 多任务 checkpoint 格式。没有证明多进程任务优先级、复杂 FSW 控制器隐藏状态、任务模式、传感器随机过程、事件与排队遥控、电池、热控和通信数据的恢复，也没有执行真实 24 小时墙钟测试。不得开放为整星生产恢复 API，`resume_supported=false` 继续保持。


## 双进程、不同优先级的原生调度恢复实验

新增 `native_multiprocess_pilot.py` 与 `test_native_multiprocess_pilot.py`，基于**两个 Basilisk 原生 SysProcess** 而非一个进程内的多个任务：

- `dyn`（进程优先级 20）：0.2 s 航天器动力学任务，包含地球中心引力、刚体航天器和三只反作用轮。
- `nav`（进程优先级 5）：0.6 s 原生 `SimpleNav` 导航任务和对应输出记录器。

源进程在原绝对时间 `t=2.0s` 捕获五组 C++ `StateData`、原生仿真时钟、各任务 NextStartTime、**两个进程分别维护的 ModelScheduleEntry.NextTaskStart**、任务/进程优先级及航天器积分时间。将有哈希校验的检查点交给一个新 Python 进程，重建两进程同构仿真图后，从原绝对时间继续运行至 `t=5.0s`。对照未中断的原生基准，五组动力学状态与后续导航时间戳/位置数据通过一致性测试；反例故意把慢进程调度条目提前，则导航输出序列与基准不同。

**关键技术边界：** Basilisk 的 `SysProcess.processTasks` 调度条目和 `SysModelTask.NextStartTime` 是独立状态，必须分别恢复、按 SWIG vector 索引写回并校验。调度循环还存在顶层 `SimModel.nextProcPriority` 与工作线程 `SimThreadExecution.nextProcPriority`：当前公开接口显示前者运行时可能一直为 `-1`，并不是线程实际执行优先级。本试验不把这个顶层字段当作可用的进程优先级检查点；验证的是两进程原生优先级、执行顺序及其调度条目，并明确声明 `thread_scheduler_priority_restored=false`。

该试验**不等于**通用多线程/任意多进程调度器恢复：仅覆盖单工作线程上的两个指定周期和优先级的原生进程。未恢复 FSW 控制器记忆、SimpleNav 等模块可能存在的隐藏状态、通用积分器内部历史、通信/热控/EPS、排队遥控、故障事件与随机序列。导入函数为内部测试专用，不对外发布恢复遥控/API。整星 `resume_supported=false` 保持不变。

代码提交 `198d6a19f3729b4768ff768277bd98338ead6a56` 的 GitHub Actions **4/4 通过**：非 Basilisk **76 passed / 1 skipped / 1 deselected**，原生 Basilisk **45 passed**，180 秒与 3600 秒加速运行均 PASS；3600 秒试验实际运行至 3601.5 秒仿真时间，输出 3602 帧遥测、7203 个原生分段。仍缺项目专用 `bsk==2.11.0+satfix1` 验证和真实 24h 墙钟稳定性证明。


## Basilisk 原生 FSW 有记忆控制器：MRP Feedback 跨进程实验

新增 `native_fsw_memory_pilot.py`，面向 Basilisk 2.11.0 原生 **C 实现的 `mrpFeedback`**。该模块即使输入姿态误差固定，内部仍保存跨调用状态：`priorTime`（上一次控制任务时刻）、`int_sigma[3]`（积分的姿态误差）和 `z[3]`（上一计算周期的积分反馈中间值）。另有在 Reset 阶段缓存的 `ISCPntB_B[9]`，以及增益、积分限幅、控制律选项和已配置反作用轮数量。本试验明确限制为 **Ki > 0、controlLawType=0、无 RW 补偿输入、固定 0.6 s FSW 周期**，从而逐一限定真实可检验的模块状态范围。

**检查点契约：** 在已推进的原生 C 模块上读取 `priorTime`、`int_sigma`、`z` 和配置指纹，用 SHA-256 对完整记录签名；恢复方必须是新初始化、尚未推进、配置一致的 Basilisk 同构模块。验证检查点绝对时刻与最后一次 FSW 调用时刻相容，不接受 NaN、格式异常、篡改、控制增益不匹配、重复导入或伪造整星恢复成功标记。真实导入仅写回试验中的有记忆字段；不伪造输入消息或修改后续计算结果。

**原生对照实验：** 复用上一轮通过的两进程动力学＋导航 Basilisk 真实模型，并在慢速导航任务增加一套独立 `mrpFeedback` 控制模块及 `CmdTorqueBodyMsg` 记录器，采用真实 `AttGuidMsg` 和 `VehicleConfigMsg` 输入。源模型在绝对 `t=2.0 s` 保存调度、动力学和 FSW 内部状态，随后不中断运行到 `t=5.0 s`；另起 Python 子进程创建全新 Basilisk 对象、重新连接相同输入消息，恢复允许的检查点后推进到原绝对 `t=5.0 s`。验证恢复控制器的**后续控制力矩时间戳及三轴数值**与不中断基准一致，并分别故意遗漏全部 FSW 记忆、`priorTime` 或 `int_sigma`，验证误差显著非零。

**不能据此声称完整闭环整星恢复：** 当前 `mrpFeedback` 是在真实 Basilisk 原生任务中运行的、有内部积分记忆的 FSW 模块，但它采用明确设定的固定姿态指导输入，并未将输出力矩反馈接入反作用轮驱动／航天器姿态闭环。因此本试验只能证明特定模块内部状态和力矩输出序列的跨进程一致性，尚未验证控制器与真实姿态／反作用轮耦合闭环、模式状态、故障与遥控时间历史，也未覆盖整个 FSW 算法组合。生产 `resume_supported=false` 必须保持。


## 原生 ADCS 闭环联合检查点与跨进程恢复实验

在既有“动力学/调度/FSW 积分记忆”单项试验之上，本阶段加入真正的 Basilisk 原生闭环：
`Spacecraft → SimpleNav → inertial3D/attTrackingError → mrpFeedback(Ki>0) → rwMotorTorque → ReactionWheelStateEffector → Spacecraft`。
动力学由高优先级 `dyn` 进程按 0.2 s 执行，指导、误差、控制分配及导航由低优先级 `nav` 进程按 0.6 s 执行。三只原生反作用轮的真实电机力矩经 Basilisk 消息输入，不使用 Python 代理动力学。原生回归验证了电机力矩确实改变轮速、本体姿态和角速度。

新增 `native_closed_loop_evidence.py` 记录并用规范 JSON SHA-256 检查**联合证据**：五组原生 `StateData`、两进程绝对调度时钟/游标、`mrpFeedback.priorTime/int_sigma/z`、最后一次 `rwMotorTorque` 电机指令，以及三只反作用轮非 `StateData` 内部字段 `Omega`、`omegaBefore`、`u_current`、`frictionTorque`。摘要用于检测记录是否改变，**不是具有密钥认证能力的数字签名**。内部测试专用写回功能只允许在未执行的原生反作用轮实例上恢复这些明确列出的字段，并逐项校验回读。

**关键发现：** 仅恢复轮速 `reactionWheelOmegas` 和最近一次电机指令消息仍然不足。Basilisk 的 `Spacecraft.UpdateState` 可以先于 `ReactionWheelStateEffector.UpdateState` 执行，动力学积分先使用每只反作用轮先前保存的 `u_current`，随后轮模块才接收新指令。若漏掉 `u_current` 等执行器内部状态，新的 Python 进程在第一个动力学步骤中就会偏离基准。首轮真实实验曾发现末态 MRP 分量约 `3.5e-4` 的误差，因此没有降低验收容差，而是补齐该原生状态并保留反例。

`test_native_closed_loop_checkpoint.py` 的跨进程回归：源闭环从 `t=0` 运行到绝对 `t=2s`，保存联合检查点并正常继续到 `t=5s`；子进程全新创建同构 Basilisk 闭环、恢复状态和上一周期执行器命令，并沿原绝对时刻运行到 `t=5s`。使用严格数值容差，同时比较航天器位置/速度/MRP/本体角速度、三轮转速、FSW 三轴控制力矩、三轮电机力矩及各对应的遥测时间戳。另分别故意遗漏旧电机指令、FSW 积分记忆和反作用轮内部记忆，要求结果与不中断基准产生可检测差异。

**生产边界：** 本试验只覆盖本文件固定的两个任务/优先级、平衡轮配置及确定性控制模式。未证明所有 Basilisk 原生模块、执行器摩擦模型/抖动模型、随机状态、真实故障过程、控制模式变化、遥控 ACK/去重与待执行队列、其他分系统和多线程运行的完整恢复。不能据此开启 `resume_supported=true`；联合证据声明依然是 `resume_supported=false`，试验恢复 API 不提供给生产用户。

**后续扩展顺序：** 第一阶段以显式控制模式状态机与边界时刻为输入，建立模式切换前后的离散状态及输出一致性；第二阶段按原生故障事件调度表恢复已发生/待发生事件及其副作用；第三阶段联合遥控事件日志、执行 ACK、幂等键和待执行队列，对异常进程中断时的每条 TC 做确定性调和。凡是执行状态无法证明的指令必须保持未决，绝不能在重启后静默重放执行。


## R6：中断会话与遥控账本的一致性预检（仍不能自动恢复）

在 R1–R5 已通过的受限 Basilisk 姿态动力学、FSW 控制器、反作用轮、控制模式、故障事件和待执行遥控联合检查点试验之后，R6 首先接入**正式持续仿真会话的持久化边界**，而不是提前开启整星原生恢复。

进程重启时，`SessionWorkspace.mark_unfinished_interrupted()` 仍将未完成会话标记为 `INTERRUPTED`，生成原有 `recovery_handoff.json`，随后写入新的 `command_recovery_preflight.json`。预检把**实际** `command_events.jsonl` 的哈希链与 **SQLite `command_ids.sqlite` 的 UNIQUE ID / 指令指纹**逐条核对，绑定原交接记录的摘要，并使用临时文件、`fsync`、原子改名生成不可自动覆盖的清单。

其中存在必须防范的事务窗口：SQLite 接受指令 ID 后，进程可能在追加 `QUEUED` ACK 之前崩溃。两种介质不是同一笔原子提交，故**不能因为 SQLite 中存在 ID 就自动判定指令已完整排队，也不能因为 ACK 日志缺少条目就重新下发**。任何不一致、无 SQLite 索引、未决 `EXECUTING`、`FAILED` 且效果不明或不完整事件链一律标记为阻断；已经 `ACKED` 的历史也不能再次执行。

只读检查命令（在项目根目录运行，`PYTHONPATH=src:.` 或已经安装项目的环境）：

```bash
python scripts/inspect_continuous_recovery.py \
  --workspace "/path/to/workspaces/SESSION_ID" \
  --command-preflight
```

加上 `--command-preflight` 后会再次核验清单、原交接记录、命令日志和 SQLite 索引是否仍一致；不修改仿真状态，不重放任何遥控。仅在人工确认源会话已经处于 `INTERRUPTED` 且缺失清单时，允许显式增加 `--create-missing` 来补建，不覆盖现有证据。状态包括 `BLOCKED_EVIDENCE_UNVERIFIABLE`、`BLOCKED_AMBIGUOUS_INFLIGHT`、`BLOCKED_UNRESOLVED_PENDING_TC` 和 `EVIDENCE_CONSISTENT_NO_NATIVE_RESTART`；**最后一种仅代表该层遥控证据一致，不代表 Basilisk 物理状态能够恢复**。

这份记录所有情况下都强制 `physical_resume_supported=false` 与 `automatic_tc_replay_allowed=false`。当前尚未把整星原生恢复状态写入生产 `SessionWorkspace`，亦未解决 SQLite 与 JSONL 的跨介质原子事务、ACK 与原生执行效果的独立证明、其他分系统状态完整序列化。旧交接格式 `interactive-recovery-handoff.v1` 和原有限时仿真均保持兼容。完整恢复资格还需要指定 `bsk==2.11.0+satfix1` 的验证、真实 24 小时墙钟试验与更多子系统状态覆盖。


## R6b：持续会话遥控接收与执行状态的 SQLite 事务化

R6a 对原始 SQLite 去重索引和 JSONL 遥控/ACK 事件进行对账，但二者不是同一事务。本阶段为**正式** `DeterministicCommandMailbox` 的持续会话 SQLite 库增加 `command_lifecycle`，把新接收指令的唯一 ID、内容指纹、会话标识、执行时间、接收顺序和初始 `QUEUED` 状态放进**同一个 SQLite 提交事务**。事务回滚时不得出现只有指令 ID、却没有初始生命周期记录的持久化半成品。

执行链路：`QUEUED` → **SQLite 提交 `EXECUTING`** → JSONL 写入 `EXECUTING` 事件 → 调用原生仿真命令接口 → 仿真继续推进 → JSONL 写入 `ACKED` 事件 → SQLite 提交 `ACKED`。任一阶段失败都不能重建出“肯定尚未执行”的假设。原生副作用执行前，持久化 `EXECUTING` 是阻止未知结果遥控重放的关键。执行异常后，`FAILED` 也不构成安全重放资格。

中断预检同时核对 SQLite `command_ids`、`command_lifecycle` 两张表与原 `command_events.jsonl` 哈希链；一个 SQLite 读取事务确保读取的是一致的数据库快照，禁止事件、目标执行时刻、状态或指纹被篡改后继续恢复。用于历史诊断的 `command_recovery_preflight.json` 会纳入生命周期表摘要；现存只含旧 ID 表、无法证明生命周期的会话也不会被静默提升为可恢复。

**未解决事项：** SQLite 与 JSONL 之间仍存在跨存储提交窗口；当前明确通过中断预检拒绝不一致状态，而不是假称两种介质具备原子一致性。内存待执行堆也没有生产级持久化重建接口。真实 Basilisk 模块全量内部状态、任务/事件队列、遥控执行效果证明、其他分系统、指定补丁版 Basilisk 和 24 小时真实运行资格均尚未完成。有限会话保持原接口兼容；整星 `resume_supported=false`、`automatic_tc_replay_allowed=false` 不变。


## R6c：权威事务事件 Outbox 与遥控 ACK 的幂等镜像

R6b 已将 `command_ids` 与 `command_lifecycle` 置于相同的 SQLite 接收事务，并在真实 Basilisk 遥控调用前强制提交 `EXECUTING`；但原有 JSONL ACK 日志与 SQLite 仍存在分开落盘的崩溃窗口。R6c 引入 SQLite 表 `command_event_outbox`，将 `QUEUED`、`EXECUTING`、`ACKED`、`FAILED`、`EXPIRED` 事件意图与对应的**权威生命周期状态变更作为一笔 SQLite 事务提交**。原有 `command_events.jsonl` 保持顺序追加与 `fsync`，只承担人可读的审计镜像；写入成功后再将该 JSONL 事件的序号、哈希填回 Outbox 的镜像游标。

控制运行时遵循“SQLite 提交 → JSONL 追加和落盘 → SQLite 镜像游标确认”的单向顺序，且 `EXECUTING` 必须早于执行真实原生控制操作。**ACKED 仅表示模拟器执行调用和该次推进已正常返回，不是证明卫星物理效应可逆、不可逆或者可重复的外部凭证。**

如果进程在**JSONL 已落盘、镜像游标尚未确认**时终止，启动时可以只核对已有 JSONL 的命令 ID、指纹、状态、仿真时刻、哈希和序号，然后补写 SQLite 游标；原始 JSONL 字节完全不变。如果在 **SQLite 已提交、JSONL 尚未写入**时崩溃，则 Outbox 仍有未镜像事件，恢复预检必须给出阻断报告：**绝不生成缺失 ACK，绝不重放原始遥控，也不将 Outbox 的 `ACKED` 直接当作物理状态可以恢复的证据**。对于镜像哈希不匹配、旧式缺失 Outbox 的数据库，均按不具备完整恢复证据处理。

实际恢复预检用同一次 SQLite 只读事务核查接收 ID、生命周期状态与 Outbox 事件链，再与 JSONL 哈希链逐事件对应；在 `command_recovery_preflight.json` 中记录 `outbox_sha256` 和事件数量。这里的摘要仅用于意外损坏检测，并不提供认证或防篡改签名。原有检查命令 `python scripts/inspect_continuous_recovery.py --workspace /path/to/workspace --command-preflight` 保持可用。

**验收边界未改变：** Outbox 完成的是遥控控制面内部状态的持久化和已存在事件的镜像校正，不能恢复任意 Basilisk 求解器状态、飞行软件隐含记忆、原生任务与事件队列或其他分系统状态；不能自动构建待执行命令堆；不能自动恢复中断后的原生仿真，更不允许重放执行结果不明的遥控。正式整星 `resume_supported=false` 与 `automatic_tc_replay_allowed=false` 继续保持。


## R6d：遥控账本单写入者代际隔离与待执行队列只读审计

在 R6c 的 SQLite 事务化 `command_lifecycle` + `command_event_outbox` 基础上，本阶段加入 `command_writer_epoch` 单例所有权表，记录递增代际编号、随机令牌及 `ACTIVE/RELEASED` 状态。持续会话打开持久化账本时，在 **SQLite `BEGIN IMMEDIATE` 写事务中**声明自己是当前唯一写入者；如果上一代仍处于 `ACTIVE`（包括进程意外退出时遗留的所有权），新实例必须拒绝接管，不采用 PID 存活推测、自动过期或超时抢占。只有上一代显式关闭并提交 `RELEASED`，才能取得下一代编号。

所有已接收指令、状态迁移和 JSONL 镜像游标的写入，都要求在对应 SQLite 提交事务中重新核对代际与令牌。旧实例即使仍持有数据库连接，只要不再是当前代际，就不能追加指令、声明 `EXECUTING` 或回写 ACK 游标；旧实例也不能释放后来者的所有权。该隔离只负责**控制面 SQLite 提交**，不代表能够实时中断正在执行的 Basilisk C/C++ 积分步骤，不能替代操作系统层的唯一进程监督、进程终止确认或物理状态一致性验证。

此外，`command_lifecycle` 在原子接收事务中保存指令完整序列化负载 `command_json`，老版本缺失的负载保持空值，绝不依据遥测重造。新增 `inspect_pending_queue()` 读取已中断工作区，首先验证原 `recovery_handoff.json` 和 `command_recovery_preflight.json`，再在 SQLite 只读事务中对仅处于 `QUEUED` 的指令检查身份、内容指纹、到期时间、原始接收顺序和当前写入者代际。仅输出按 **执行时间、接收序号** 排序的候选元信息，不构建可执行内存队列。

可使用现有审计命令查看：

```bash
python scripts/inspect_continuous_recovery.py \
  --workspace "/path/to/workspaces/SESSION_ID" \
  --pending-audit
```

其中 `--pending-audit` 会一并执行 `--command-preflight` 的只读核验。审计结果中的 `CANDIDATE_METADATA_VERIFIED_NO_NATIVE_ACTIVATION` 仅表示候选遥控具有原始入库证据和可确定排序，绝不等于恢复执行许可。若历史指令缺少原始负载、存在 `EXECUTING/FAILED` 未知效果、预检不一致、缺少原生遥测时间或候选执行时间不晚于最后可观察的原生轨迹，则报告阻断。所有结果强制 `activate_native_queue_allowed=false`、`automatic_tc_replay_allowed=false`、`physical_resume_supported=false`。

**尚待解决：** 真实进程异常退出后如何由外部监督器可靠确认旧运行主体已停止；完整 Basilisk 原生模块状态、积分器、任务/事件队列与消息历史的全所有者一致恢复；遥控执行效果证明；经审定的新会话代际与旧会话数据隔离；项目指定补丁版 `bsk==2.11.0+satfix1` 的验收及真实 24 小时连续运行。R6d 不提供强制抢锁、自动重放或生产级整星恢复入口。


### R6d 启动时的特殊阻断

恢复检测还加入了**双服务实例保护**：当同一持续会话的 SQLite 写入者标记为 `ACTIVE`（可能仍在正常运行，也可能意外退出后遗留）时，其他管理器不能擅自把该会话的状态日志追加为 `INTERRUPTED`，更不能生成看似完整的恢复证据。该工作区只会返回 `TC_WRITER_ACTIVE_OR_ORPHANED_NO_AUTOMATIC_INTERRUPTION` 阻断信息，不修改旧会话历史。旧版数据库缺少可信所有权表时同样采取安全阻断策略。

一旦出现此情况，不能仅凭 PID 不存在、等待超过某个超时时间或界面显示“未运行”就强制抢占。正式恢复必须先由外部进程监督设施确认旧原生运行主体已终止，再制定经过审核的代际交接流程；当前实现故意**不提供**这条自动路径。


## R7a：原生子进程终止栅栏与受限联合检查点实验

此前 R5 已证明，在确定性 Basilisk 双进程／三只反作用轮 ADCS 图中，经过显式恢复原生时钟、姿态动力学、FSW 积分器记忆、执行器内部记忆、故障链路和待执行遥控，新的 Python 进程可以在原绝对仿真时刻继续得到与不中断基准一致的输出。但原 R5 试验没有把**源仿真的 OS 进程生死与恢复准入**联在一起。

R7a 新增内部受限监督器 `native_process_supervisor.py`。父进程通过 `subprocess.Popen` 启动独立的子进程，保存实际进程句柄和随机启动 nonce。子进程以 Basilisk 原生模型推进至检查点后，将自身 PID、nonce、受限模型 Profile、绝对仿真时刻和检查点 SHA-256 落盘作为就绪回执。父进程必须验证回执与**自己持有的 Popen 对象**一致；随后显式请求终止，调用 `Popen.wait()` 取得该子进程的实际退出状态，再生成一次性、`fsync` + 原子改名的 `basilisk-direct-child-reap-barrier.v1` 证据。

**不能用 PID 不存在、PID 查找、文件已经存在或固定超时推断“原进程一定已终止”。** 只有父进程确实持有并等待回收了它创建的那个子进程，才允许本试验写入终止证据。如果在握手前退出、握手身份不对、子进程迟迟不能回收、证据暂存文件残留，或宣称完整整星自动恢复，则必须失败。Linux/macOS 实验还通过新建进程会话和进程组发送终止信号，但目前**不声称已经证明所有可能的脱离进程组的后代、外部服务、硬件执行或线程外部资源都已终止**。

新增 `test_native_supervised_process_barrier.py`：不是纯 Python 代理仿真。真实 Basilisk 子进程加载 `Spacecraft`、`mrpFeedback`、`rwMotorTorque` 和三只 `ReactionWheelStateEffector` 的闭环，在 t=2.0s 生成 R5 故障/模式/待执行遥控的联合检查点，停留在进程内。父进程在检查点存在时仍拒绝将文件视为终止证明；随后实际终止并回收源子进程，验真检查点和终止栅栏之后，才**仅在隔离试验**启动全新 Python 进程导入受限检查点，运行到 t=5.0s，并对照独立不中断 Basilisk 基准的姿态、角速度、轮速、FSW 力矩、轮电机指令时间戳和最终动力学状态。漏握手、证据篡改、伪造 PID、重复写入终止证明都应拒绝。

**验收范围与边界：** 此栅栏只能证明**父进程直接监管的一个子进程已被 wait 回收**；SHA-256 只用于检测无意或未经重新计算的内容变化，不是外部身份认证或安全签名。它既不能通过离线核验再次证明当前不存在另一个进程，也不能保证原生状态覆盖任意 Basilisk 模块。当前正式 `SessionWorkspace` 的 Basilisk 仿真仍运行在原有管理架构中，尚未迁移为由新监督器直接持有的独立原生子进程，因此本试验**没有为生产级自动恢复建立完整资格**。原有 `command_writer_epoch` 异常 ACTIVE 所有权继续不可自动抢占，`resume_supported=false` 与 `automatic_tc_replay_allowed=false` 不变。下一阶段必须设计真实运行主体的进程隔离、原生所有状态所有者的恢复准入、会话/遥控代际交接，以及指定 `bsk==2.11.0+satfix1` 和真实墙钟长期运行验证。


## R7b：正式持续运行图的独立原生子进程隔离（部署端显式启用）

R7a 证明受监督进程在受限三轮 ADCS 试验场景可以经父进程真实回收后在另一进程完成等价恢复，但尚未接入 `InteractiveSession` 正式运行时。R7b 新增可选的 `SupervisedContinuousNativeRuntime`，实现既有 `PersistentSimulationRuntime` 协议，**父进程仍负责会话生命周期、用户遥控校验、SQLite `command_lifecycle` / Outbox、ACK 与遥测存储；真正的统一 Basilisk 原生模型只在单个独立 Python 子进程中创建、推进和关闭**。

默认调用 `build_persistent_runtime(spec)` 不变；只有部署进程明确设置环境变量 `SAT_SIM_SUPERVISED_NATIVE_RUNTIME=1`，且会话属于 `whole_spacecraft.unified_native.v1` 与 `continuous=true`，工厂才返回该隔离适配器。也可在测试/受控内部调用中以 `build_persistent_runtime(spec, supervised=True)` 明确选择。任务规格 `task_spec` **不能**携带任意执行程序、可变进程命令或决定是否启用隔离功能；子进程固定调用内置 `build_persistent_runtime(spec, supervised=False)`，避免递归再启动。当前阶段是技术预览，生产运行环境需单独评估资源、时延和进程组管理。

子进程使用 `multiprocessing.spawn` 而非继承父进程内可能不安全的 Basilisk 模型状态；父进程始终保留原始 `Process` 对象。初始化时用随机启动 nonce、真实子 PID 和消息协议版本完成握手；后续 `prepare`、`apply_command`、`advance_to`、`read_delta`、`audit_native_checkpoint_coverage`、`finalize`、`abort` 均通过**有序单一请求序号**交互。每次回应要验证原始子进程标识、nonce、序号和消息结构。该进程间通道仅面向同机父子进程，不暴露网络接口；它不是未经信任客户端可直接操作的远程 RPC 服务。

父进程先于原生 `apply_command` 在 SQLite 中提交 `EXECUTING` 栅栏，随后通过子进程执行本机 Basilisk 指令，再等待 `advance_to` 返回，按照 R6c 事件事务与 JSONL 镜像记录 ACK。**如果请求发送失败、子进程死亡、回包错乱或应答超时，指令效果均视为不确定；父进程禁止重发该请求、不得自动重建 Basilisk 图，并使用真实 `Process.join()` 回收持有的直接子进程。** 正常 `finalize` 要求子进程退出码为零且回收完成。子进程异常退出造成会话 `FAILED` 时，原 `command_writer_epoch` 的持久所有权保持 `ACTIVE`，不会被异常清理误置为 `RELEASED`，从而阻止新实例以干净交接的假设接管。

与之前不同，R7b 已把**真实连续会话经子进程执行原生统一仿真**连接起来，增加真实 Basilisk 跨进程与直接进程内运行的遥测一致性试验，以及父进程 SQLite 指令账本、ACK 和遥测归档闭环试验；该模式不需要伪造一个纯 Python 卫星物理模型。

**重要边界：** 这是原生计算进程隔离，不是跨进程自动恢复。普通 `InteractiveSession` 的父工作线程仍持有 SQLite 及会话状态，若父进程整体死亡，子进程与进程树的全面停机、SQLite 异常代际确认仍需额外 OS 监督设施。虽然能通过父进程主动终止并回收它直接持有的子进程，但不能保证已脱离的进程后代或外部设备停止，也不能证明 Basilisk 的所有积分器与分系统隐藏记忆均被原生检查点覆盖。`resume_supported=false`、`automatic_tc_replay_allowed=false` 不变。启用隔离模式并不等于已经具备生产级持续恢复能力。


## R7c：Linux 原生运行子进程的父进程死亡栅栏

在 R7b 现有的 `SAT_SIM_SUPERVISED_NATIVE_RUNTIME=1` 隔离通道上，R7c 增加 Linux 内核级的原始父进程生存依赖。真实 Basilisk 计算子进程在构建任何原生模型和发送就绪回包**之前**调用 `prctl(PR_SET_PDEATHSIG, SIGKILL)`，并检查操作系统记录的父 PID 与父进程传来的启动身份一致。前后各做一次 `getppid()` 校验，因为“检查父进程仍在 → 注册死亡信号”的两步之间可能发生死亡竞争；发生竞争或系统调用失败时，拒绝建立新的 Basilisk 模型。

Linux 内核随后在该子进程的**直接父进程死亡**时向其发送 `SIGKILL`。这一机制不依赖进程是否正在处理 Python RPC；即使处于原生 C/C++ 积分段，也不因 Python 事件循环未调度而遗漏死亡信号。子进程就绪回包明确标注 `parent_death_fence.supported` 和 `kind`，父进程按同一次创建时的真实 PID、随机 nonce 和平台要求核验后，才下发 `prepare`。Linux 上无法证明内核栅栏已安装则启动失败并回收子进程。

新增真实 Basilisk 父进程 `SIGKILL` 故障注入：独立启动正式 `InteractiveSession` 与 SQLite 遥控账本，建立真实 `whole_spacecraft.unified_native.v1` 子进程并排入一条未来遥控。随后在不调用正常 `abort` 或 `stop` 的情况下杀死**持有会话和账本的父进程**，使用 Linux `/proc` 的 PID 与进程创建时钟排除 PID 重用，确认原生子进程消失或进入僵尸等待回收状态；同时验证原会话 SQLite writer 仍处于 `ACTIVE`，待执行遥控仍为 `QUEUED`、没有被伪造为已执行，新管理器不得改写原会话事件或抢占写入者。该故障注入基于真实 Basilisk，不使用纯 Python 运动学作为物理数据。

**平台边界：** `PR_SET_PDEATHSIG` 只适用于 Linux。本阶段不声称 Windows/macOS 拥有等效父进程死亡保障（分别需 Job Objects 或其他经验证的本机监督设施）；这些平台上的实验运行若没有外部监督，`parent_death_fence.supported=false`，不能据此认定为具备生产安全接管条件。父进程死亡信号只发送给**直接子进程**，不能证明它自己创建的脱离后代、操作系统外部服务或硬件设备已经停止；父进程整机断电也没有机会保证检查点原子落盘。Linux 上观察到僵尸状态意味着进程已经停止执行，但仍有待系统 init 回收的进程表项。

这项隔离加强**持续运行中崩溃后的停机安全性**，不是恢复可用性的证明。当前生产级完整整星重启仍受 Basilisk 模块/FSW 内部状态覆盖不足、原生任务/事件队列恢复、原子检查点与遥控所有权代际接续等限制。仍然强制 `resume_supported=false` 和 `automatic_tc_replay_allowed=false`；任何异常残留 `ACTIVE` 会话都不能被自动接管。指定 `bsk==2.11.0+satfix1` 与真实长时间墙钟验收尚待完成。

## R7d：Windows 子进程保护与“持续卫星仿真”新页面

Windows 平台使用 native_windows_job.py，在独立原生子进程创建后、首次 prepare 调用前，将它分配进启用 JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE 的专属 Windows Job Object。父进程持有唯一的 Job 句柄直到子进程关闭；父进程异常死亡会导致 Job 句柄关闭，操作系统负责终止 Job 内进程。Job 创建、配置或进程分配失败时拒绝启动，没有静默降级。必须由 Windows CI 专项验证，不能用 Linux CI 作为 Windows 结论。

工作台左侧新导航“持续卫星仿真”独立于已有“实时会话”，支持无代码创建原生整星持续会话（会话 ID、仿真量子、倍率、墙钟节拍、初始化时长），选择会话并启动、暂停、继续、单步或停止归档；实时观察轨道半径、指向误差、电池 SOC、进程 PID、写入者代际、内核保护能力、归档状态，以及中断工作区和会话事件。遥测按原生流序号续读、显示 GAP，不生成代理物理数据。遥控表单可指定目标姿态、整星运行模式、ADCS 控制使能和经授权的故障注入，执行时刻为绝对仿真秒数，提交前二次确认；后台仍使用既有注册指令/角色校验及 SQLite 事务 Outbox 和 ACK。

新增受约束的 REST 接口：
- GET /interactive/continuous/overview：连续能力、部署方式、会话及中断工作区安全摘要。
- POST /interactive/continuous/sessions：由服务端生成批准的原生整星 TaskSpec，不能上传任意执行脚本。
- GET /interactive/continuous/sessions/{session_id}/status：会话、进程、保护标志、遥控写入者代际，只读。
- 操作、遥控和遥测复用现有 /interactive/sessions/{id}/control、/commands 和 /telemetry/{stream} 接口。

启用 SAT_SIM_INTERACTIVE_ENABLED=1 后导航可见。默认进程内运行保持不变，只有部署端开启 SAT_SIM_SUPERVISED_NATIVE_RUNTIME=1 才使用跨进程 Basilisk。Windows Job Object 不能证明无关进程、脱离 Job 的服务或外部执行效应可恢复；Linux 的死亡信号只保护直接子进程。继续强制 native_resume_supported=false 和 automatic_tc_replay_allowed=false。尚需项目 Basilisk 补丁版和真实 24 小时墙钟运行、完整原生检查点、经验证的代际交接等验收。


## R7e：持续运行墙钟时间与资源可观测性（只读）

在工作台的「持续卫星仿真」页面新增「真实运行与资源监测」区域，并增加 \`GET /interactive/continuous/sessions/{session_id}/observability\`，其职责为**读取真实证据，不控制或重新创建 Basilisk 计算图**。该接口返回：

- \`wall_elapsed_s\`：基于 Python \`time.monotonic()\` 的本次进程内会话创建后真实墙钟秒数，包括准备、暂停和运行；不等同于实际主动积分时长。
- \`sim_elapsed_s\`：原始 Basilisk 运行器的累计仿真时间；不能用来宣称现实持续运行了相同小时数。
- \`process\`：受监督模式读取**仍由当前父进程持有且存活的** Basilisk 子进程资源；进程内模式则读取包含 API 与 Basilisk 的父进程整体资源。Linux 使用 \`/proc/<pid>/stat\`，Windows 使用 \`GetProcessTimes\` 和 \`GetProcessMemoryInfo\`，报告 RSS/Working Set 常驻字节数及累计 CPU 秒数（不是 CPU 占用百分比）。系统不支持或进程已退出时返回 \`available=false\`，绝不把旧 PID 当成仍在运行的进程。
- \`telemetry\`：从既有 \`TelemetryBus\` 中读取最后一条**真实**指定流帧的仿真时刻和 UTC 入站时刻，计算当前墙钟滞后；READY/PAUSED 期间标注 \`PAUSED_OR_READY\` 而不是错误宣称中断。状态可能为 \`NO_TELEMETRY\`、\`FRESH\`、\`LAGGING\` 或 \`TERMINAL\`。
- \`durable_frame_count\` 与 \`durable_bytes\`：从 \`SessionWorkspace\` 加锁读取已 \`fsync\` 的遥测计数与当前/旋转分段累计写盘逻辑字节数，**每次刷新不重新扫描增长中的 JSONL**。
- \`disk\`：工作区所在文件系统的当前可用字节、总字节与遥测写盘预留门限。该时点的可用空间不保证未来可写；数据无法读取时显示不可用，不得估值代替。

前端以与原有会话状态相同的轮询节奏刷新各项指标，未实现任何自动重放、隐式退出恢复或将 CPU 累计秒误解释为负载百分比的逻辑。新增后端单元测试核实**真实单调墙钟流逝**、原始 SQLite/JSONL 写盘计数和真实遥测时间戳；Chromium 测试核实指标在用户界面出现。真实原生 Basilisk 和长仿真时长仍由原生 CI 独立测试。

**R7e 不是 24 小时现实世界连续运行资格认证。** 它只是为接下来的墙钟长稳测试提供可查询的证据采集接口；真正的 24h 墙钟验证必须另建连续进程测试，采样并留存外部证据，核验无额外 TC 重放、遥测断点、内存持续增长、写盘故障与意外崩溃。


## R7f：原生持续仿真长稳验收证据采集与导出

在「持续卫星仿真」页面增加长稳验收证据区：操作员选择真实墙钟采样间隔（1、2、5、10、30、60 或 300 秒），点击「开始证据采集」，由**服务端独立只读线程**定时观察已有持续会话，不依赖浏览器保持打开。期间可以继续操作原生 Basilisk 仿真，不改变原有遥控数据库、物理状态或模拟时钟；点击「停止并生成摘要」只结束证据采集线程，**不会停止卫星仿真**。

采样写入每个持续会话工作区的 \`continuous_endurance_evidence.jsonl\`，每条记录包含真实 UTC 时间戳、单调墙钟运行时长、独立的仿真时间、原生进程当前 RSS/CPU 累计秒、最后真实遥测及延迟、持久化遥测帧数/字节数、磁盘空间；采用连续 sequence、previous_hash、entry_hash（SHA-256）与 \`fsync\` 的追加写入。停止时写入 \`continuous_endurance_summary.json\`，记录采样时间跨度、采样最大间隔、最大遥测滞后、磁盘可用空间最小值、RSS 起始/末尾/峰值、发生过的告警、完整证据链尾哈希和人工验收资格。两种文件均可通过网页按钮下载。SHA-256 用于发现内容意外损坏，不是远端身份认证/数字签名。

API:
- \`POST /interactive/continuous/sessions/{session_id}/endurance/start\`，body \`{"sample_interval_s":5}\`，须操作权限；仅可开始一次，绝不覆盖已有历史证据。
- \`POST /interactive/continuous/sessions/{session_id}/endurance/stop\`，停止采样并等待摘要写出，不停止原生卫星。
- \`GET /interactive/continuous/sessions/{session_id}/endurance/status\`，查看采集状态、最新观测、告警和摘要状态。
- \`GET /interactive/continuous/sessions/{session_id}/endurance/evidence\`，下载 JSONL 样本；\`.../endurance/summary\`，下载已完成的摘要。

监测会为运行中的遥测非新鲜/无进度、磁盘空间低于预留值、进程指标不可获取、真实采样时间间隔过长、采集器 I/O/状态异常记录告警。暂停/准备阶段不会因没有新遥测误触发停滞告警。已完成至少 24 小时真实墙钟、采样完整、无告警、会话正常完成，最多产生 \`eligible_for_manual_24h_review=true\`，需要人工复核原生连续性/轨迹、TC 幂等性、文件完整性和硬件/平台证据。报告字段 \`qualified_24h_wallclock=false\` 目前固定不自动判通过。

**限制：** 该证据采集运行在当前后端进程内；如果服务端崩溃，采样停止，原有追加文件可能存在未完成记录，必须判为 \`INCOMPLETE\` 并做完整哈希链检查，不可伪造正常停止摘要或重启后自动续写旧证据。不存在自动 Basilisk restart、远程 TC replay 或 SQLite writer generation 强制接管。持续运行达标仍需真实 24h 墙钟、检查点原生全状态覆盖以及指定 Basilisk 补丁版的验证。


## R7g：独立进程长稳证据审计、增长趋势与30秒真实墙钟准入

R7f 收集的 JSONL 与摘要，不仅能在持续仿真前后下载，还可以由**与 Basilisk 服务完全分离的 Python 进程**只读审核，即使原仿真服务已经崩溃也无需启动新仿真、连接遥控 SQLite 写入者或访问原生 C++ 模型。

以原始会话工作区（包含 \`continuous_endurance_evidence.jsonl\` 与 \`continuous_endurance_summary.json\`）为参数，在源码仓库根目录执行：
\`\`\`bash
PYTHONPATH=src python -m sat_sim.interactive.continuous_endurance_audit /path/to/session-workspace
\`\`\`
审计运行时仍在采样，可额外加 \`--allow-incomplete\`（仅将 INCOMPLETE 的退出码改为 0，**不会**变成已通过）；自定义采样失联检测门槛可用 \`--max-stale-s 30\`，自定义内存增速**预警**可用 \`--rss-warning-mib-h 512\`。审计每次返回单行 JSON，过程纯只读且不以进程 PID 推断是否可恢复。返回状态：

- \`INCOMPLETE\`：没有采样，或仍未生成正式摘要，包括崩溃后的残留证据；不能据此宣称已通过长稳验收。默认命令退出码 3。
- \`BLOCKED\`：哈希链、摘要或各样本的状态、时间、遥测序号/帧计数互相矛盾、非法/截断；退出码 2，阻止人工通过证据链。
- \`NOT_QUALIFIED\`：证据可读且有正式摘要，但真实 RUNNING 墙钟不足，或者发现采样间断、遥测停滞、进程读数缺失、磁盘不足、内存增速预警等；退出码 0 只代表审计命令成功执行，**不代表运行已达标**。
- \`REVIEW_ELIGIBLE\`：观察的 RUNNING→RUNNING 累计真实秒数至少 86400，证据链/摘要完整，正常结束、无告警、采样间隔合格。仍然不是自动通过，需要独立人工检查 Basilisk 物理状态、遥控账本一致性和平台版本。全程 \`qualified_24h_wallclock=false\`、\`automatic_tc_replay_allowed=false\`、\`automated_recovery_allowed=false\`。

审计对所有观测文件按流式遍历，内存开销不随长稳文件长度无限增长；核查同一原会话、遥测 stream、仿真进度、物理遥测序号、磁盘容量、RSS 起始/峰值/末尾和每小时增长率。增长率仅为**首尾 RSS 差值除以实际墙钟跨度的简单趋势预警**，不能当作内存泄漏的统计证明；单一进程 CPU 累计值不是 CPU 百分比。若需更可靠的趋势估计、长稳异常分组，应对导出的完整证据另行统计分析。

网页「持续卫星仿真 → 长稳验收证据采集 → 独立核验现有证据」也可以手动调用同一个只读审核逻辑（不会自动逐秒扫描长文件），显示证据完整性结论和 RSS 增速。**原进程崩溃后应优先使用外部 CLI**，因为网页 API 依赖原服务仍在运行。SHA-256 哈希链并非不可伪造的数字签名；持有完整文件编辑权限的攻击者可以重写整条链。

CI 除原有8秒真实墙钟原生短测外，额外对**实际运行30秒墙钟**的真实 Basilisk 会话进行连续采集；必须由另一个 Python 进程执行原始证据 CLI 审计，并留存样本和哈希摘要。30秒依然只是阶段性准入测试，绝不等同于真实24小时长稳通过。项目定制 bsk==2.11.0+satfix1 和整星原生检查点完整覆盖仍未验收，继续保持生产自动恢复关闭。


## R7h：原始事件与遥控事务账本跨源一致性审计

持续长稳验收不能只证明 \`continuous_endurance_evidence.jsonl\` 内部哈希正确。即使周期性采样看起来持续运行，原始 \`state_events.jsonl\` 可能记录了两次采样之间的 \`PAUSED\`，或原始遥控 \`command_events.jsonl\` 与 \`command_ids.sqlite\` 中已提交的生命周期、Outbox ACK 镜像不匹配。这些异常现在会阻断长稳资格。

独立命令不变：\`PYTHONPATH=src python -m sat_sim.interactive.continuous_endurance_audit 原始会话工作区\`。R7h 在**已经完成摘要**后追加以下只读核对（正在持续采集、原 SQLite 仍可能发生事务变化时，先只报告 \`INCOMPLETE\`，不把跨存储瞬时视图当最终结果）：

- 核实 \`session_spec.json\` 的原始会话 ID 和 continuous 标志，以及 \`state_events.jsonl\` 的 SHA-256 哈希链、连续事件序号、状态版本、仿真时间单调性、UTC 事件时间。若在采样窗口内存在原始 \`PAUSED\`、\`FAILED\`、\`ABORTED\` 或 \`INTERRUPTED\`，即使采样文件没记录到该状态，也标记 \`ORIGINAL_STATE_PAUSED_OR_INTERRUPTED_IN_WINDOW\`，禁止判为不间断 24 小时。
- 通过 SQLite \`mode=ro\` + \`PRAGMA query_only=ON\` + 一致性读事务核查原始 \`command_ids\`、\`command_lifecycle\`、\`command_event_outbox\`、\`command_writer_epoch\`，绝不重写历史、修补 SQLite、抢占所有权或重播指令。
- 使用原始 \`command_events.jsonl\` 哈希链和每条 ACK 中保存的原始遥控字段，与 SQLite 指纹、QUEUED/EXECUTING/ACKED/FAILED/EXPIRED 状态及 Outbox 的镜像序号、哈希和仿真执行时刻交叉比对。若 SQLite 表示 ACKED，但 JSONL 不存在对应的完整确认，或 Outbox 镜像已变更，结论为 \`BLOCKED\`（完整证据不可信），**不能根据某一个账本擅自推断物理执行成功**。
- 若所有源的结构和记录彼此一致，但原会话尚未正常 \`COMPLETED\`、写入者代际仍是 \`ACTIVE\` 或存在未最终 ACKED 的指令，会在人工验收判据里记为“不合格”，而不是将其解释为允许自动恢复。会话仍在 RUNNING 时状态事件只在状态切换/心跳出现，因此不会要求每个状态事件追上逐帧遥测；只有终止后的原始状态时间才用于末尾仿真时间核对。

页面「持续卫星仿真 → 独立核验现有证据」新增原始状态事件数量、SQLite 已接受遥控数量、ACK/Outbox 对应数量和核验状态。审计结束产生的报告不泄露 SQLite writer token、原始遥控参数或操作员凭据。外部 CLI 即使服务端不在仍可审查历史原件。

**验收边界：** 原始数据跨源一致性可减少观测间隔漏报与账本不一致风险，但绝不等于“任意一次 ACK 都代表实际已完成物理效果”，也不代表 Basilisk 原生积分器、FSW 内部状态、任务调度器以及执行机构状态已经具备可恢复快照。保持 \`qualified_24h_wallclock=false\`、\`native_resume_supported=false\` 与 \`automatic_tc_replay_allowed=false\`。


## R8-准入阶段：整星原生检查点所有者覆盖与受控恢复门禁

本阶段不把遥测值或局部反作用轮状态误称为完整 Basilisk 检查点。在已有真实原生检查点只读审计 \`GET /interactive/sessions/{id}/checkpoint/coverage\` 基础上，新增 \`GET /interactive/continuous/sessions/{id}/recovery/readiness\`（操作员权限）：要求会话已经**正常推进且处于 PAUSED**，只读取原 Basilisk 工作线程的本机状态审计，不会暂停运行中的会话、不会更改积分器、不会重建图、不会接管遥控或者自动重新执行遥控。

新增模块 \`native_recovery_readiness.py\` 把原始 Basilisk 实时审计与如下必须恢复的所有者逐项绑定：
1. 调度器与积分器的时钟/任务队列/事件队列
2. 航天器动力学与动态效应器
3. ADCS 反作用轮（含内部记忆）
4. ADCS FSW 与控制器内部记忆
5. ADCS 传感器与噪声状态
6. EPS 电池与功率网络
7. 热网络积分状态与历史
8. 通信和存储队列
9. 推进机构、燃料与控制
10. 故障与事件时间轴
11. 待执行遥控、幂等去重及 SQLite 写入者代际
12. 随机数生成器状态

每类分别列出真实可读**观测**、完整**状态导出**、新进程**状态导入**和与不中断运行的**数值一致性证明**。在当前 Basilisk 原生整星中能读取的轨道/姿态、部分控制增益、电池与存储量、原生 3RW StateData 子集和本机调度相位只算观测。过去通过的 R5 固定 3RW ADCS 跨进程恢复实验属于**受限研究原型**，不是这一套包含 EPS、热、通信、推进、事件和原生隐藏状态的整体恢复许可证。因此报告目前严格为 \`BLOCKED\`、12 个必需所有者、0 个已完整证明可恢复；自动恢复、自动 TC 重放和原会话跨进程接管一律为 false。

报告带有两层校验：先检验原始实时审计的 SHA-256 摘要、状态所有者顺序与「恢复未证明」约束，再验证 Basilisk 原生调度时钟与报告仿真秒数一致，输出带 SHA-256 的机器可读准入矩阵。修改状态为恢复已完成，或伪造本机所有者支持完整导入/恢复，会被阻止。其摘要是本地完整性校验，不是加密身份签名。

前端「持续卫星仿真 → R8 原生中断恢复准备度」支持暂停会话后点击「检查原生恢复覆盖」，显示必需所有者、已证明恢复数、每位所有者的未完成条件、原生采样时刻，并可下载 JSON 缺口清单。**不提供恢复运行按钮**，防止页面把未实现的功能标为可用。正在 RUNNING、未推进、未授权或已结束的会话不允许调用该能力。

当前工程下一步仍需真正的「完整原生联合检查点导出、跨进程导入、物理状态/控制器/事件/遥控状态不间断对照」；必须包括异常注入、旧子进程退出、SQLite 所有权核查及控制效果唯一性，全部通过后才可以讨论受监管恢复，不允许先开关后补证据。指定 Basilisk 项目补丁轮子仍需独立环境校验。

## R8-C：反作用轮单机真实原生硬件初值与命令能力上限

R8-B 已开放的 \`rw_max_torque_nm\` 之前仅传给项目的 RW command fault manager；Basilisk \`simIncludeRW.rwFactory.create("Honeywell_HR16", …)\` 自身一直硬编码 \`u_max=0.2\`。因此此前用户调小限制时，下游命令会被限制，但不能说原生硬件 \`u_max\` 也同步变化。R8-C 纠正此建模不一致。

现在创建一份新的持续会话时，\`initial_configuration.adcs\` 允许设置：
- \`rw_configuration\`：\`orthogonal_3\` 或 \`pyramid_4\`；本轮不允许任意新增/删除不受支持的硬件型号；
- \`rw_max_torque_nm\`：正数且不大于 0.2 N·m，**同时**传入 Basilisk Honeywell_HR16 \`rwFactory.create(u_max=…)\` 和下游 RW 命令/故障管理器，且有原生建模级兜底验证；
- \`rw_initial_speed_rad_s_0\`、\`_1\`、\`_2\`：分别设置 RW1、RW2、RW3 原生 \`Omega\`，单位 rad/s，允许 -500～500；默认分别为 10.4719755、20.9439510、31.4159265 rad/s（对应原 Basilisk 工厂传入的 100/200/300 RPM）；
- \`rw_initial_speed_rad_s_3\`：只在 \`pyramid_4\` 时允许配置 RW4 初始原生 \`Omega\`；默认 41.8879020 rad/s（原工厂的 400 RPM）。三轮构型传入 RW4 单独设置会收到 HTTP 422，而不是被静默忽略。

**Basilisk 单位换算：** `simIncludeRW.rwFactory.create` 的 `Omega` 实参表示 RPM（转/分），而实际 `rwSpeedOutMsg` / 整星遥测是 rad/s。接口先校验用户的 rad/s，再通过 `Omega_RPM = Omega_rad_s × 60/(2π)` 转成原生工厂需要的 RPM。CI 的真实 Basilisk 轮速验证曾明确发现漏换算会产生 10 倍左右的误差（100 RPM = 10.4719755 rad/s），本轮加入该换算并以实际物理遥测验证，**不是简单调整测试阈值**。

专用工作台运行前配置表单只有在选择四轮金字塔时才会显示/启用 RW4 输入框；三轮正交时禁用并从提交数据中剔除。实时整星遥测曲线也增加 RW1～RW3 的真实 Basilisk 轮速以及 RW1 下游命令有效扭矩限幅（两者来源不同，界面分别命名）。

验收采用真实 upstream Basilisk 的不同初值对照：不仅检查源配置，还检查完整原生计算图输出的 \`adcs.rw.speed_rad_s_0\` 与默认轮速确实不同，并且透明包裹 \`simIncludeRW.rwFactory.create\` 记录实际传给 *官方 Basilisk 反作用轮模块* 的 \`Omega\`、\`u_max\`，再调用原始函数构造物理模型。该捕获不代替实际物理推进或速度遥测。之前受限 R5 原生检查点和整星未准入恢复策略保持不变。尚未加入摩擦、轴承寿命或电机电气模型的任意自定义参数，这些需要先做 Basilisk 原生组件赋值及差异实验。


## R8-D：四轮原生遥测和持续会话曲线闭环

R8-C 虽已允许在整星原生构型中安装 RW4、设置独立初始轮速，但原持续会话的公开遥测列名和曲线选项还只有 RW1～RW3。R8-D 让这两端与物理构型一致，且不改变原有布局：

- 当且仅当创建会话时采用 `initial_configuration.adcs.rw_configuration="pyramid_4"`，`whole.continuous` 的输出字段声明增加 `adcs.rw.speed_rad_s_3` 和 `adcs.rw.effective_max_torque_nm_3`；三轮构型仍仅声明真实存在的三轮数据。
- 这两个字段来自现有 `UnifiedNativeRuntime` 中 Basilisk `ReactionWheelStateEffector.rwSpeedOutMsg` 及项目已连接的真实 RW 命令限幅消息，未生成任何替代物理遥测。RW4 曲线选项在页面初始状态不可用；只有当前会话收到包含有效 RW4 速度的遥测帧后，才能选择，切换回三轮会话时重置。
- 对照测试在两份独立的、真实 upstream Basilisk 2.11.0 四轮整星计算图上分别配置 RW4 初速及电机最大力矩，核对四只原生轮的实际创建参数、rad/s↔RPM 单位边界、第四轮物理速度遥测及命令有效限幅。浏览器端另用明确标记的协议替身只测试界面行为，不将替身结果当作物理验证。

此改进**仅**闭合四轮运行时可观测性，不构成四轮跨进程检查点一致性或整星恢复许可。运行中的硬件重配置、自动重放遥控、24 小时真实墙钟验收和原生整星状态恢复均保持原有安全限制。


## R9-A：真实四轮 ADCS 闭环跨进程恢复研究试验

本阶段仅扩展 **隔离 Basilisk ADCS 研究图** 的跨进程试验能力，不开放 HTTP 恢复端点。原有 R5 闭环证据模块过去将反作用轮数量固定为 3；现在允许严格的 **3 或 4** 轮验证，检查原生 C++ `reactionWheelOmegas` 状态向量、`ReactionWheelData` 内部可读字段、`mrpFeedback.rwConfigParams.numRW` 和控制力矩消息的个数必须一致。不同拓扑和重新计算摘要后的数量伪造均应拒绝。

新增 4RW 金字塔真实闭环研究试验：Basilisk `Spacecraft + 4 Honeywell_HR16 RW + SimpleNav + inertial3D + attTrackingError + mrpFeedback + rwMotorTorque`，分别运行两个不同周期的原生任务。源进程在 2.0 秒记录原生状态、调度相位、控制器积分记忆、RW 可暴露内部状态及原生电机输出，再不中断推进至 5.0 秒。独立操作系统进程新建同构 Basilisk 图并恢复上述试验状态，检验后续真实姿态、角速度、FSW 力矩、四轮电机命令和四轮转速的逐时刻差异，并通过故意不恢复控制器记忆或电机保持命令的反例，检查实验是否对缺少关键状态敏感。

**边界：** 即使隔离图对照通过，也不证明整星恢复——未覆盖统一整星计算图全部调度任务、原生导航/传感器历史、EPS/热/通信/推进状态、故障与随机数、SQLite TC 所有权与执行效果，以及未知 Basilisk 私有内存。原有 R8 12 个整星恢复必需所有者继续处于 `BLOCKED`，不改变 `resume_supported=false`、不开放自动恢复与遥控重放。本阶段需以 GitHub 原生 CI 实测结果判定是否验收。
