## 00｜完全新手从这里开始

## 本课目标

不学习任何内部架构，只完成四件事：

1. 启动 V15；
2. 打开图形组装；
3. 运行一个已经验证过的 ADCS + Reaction Wheel 模型；
4. 找到运行结果。

完成本课以后，你就知道 V15 的基本使用方式。

---

## 1. 先确认你使用哪个目录

推荐使用独立的 V15 项目目录，例如：

```text
D:\Project\sat-platform-visual-composer-v15
```

或 Linux：

```text
/home/user/project/sat-platform-visual-composer-v15
```

如果你已经有旧 SAT 项目的 `.venv`，继续复用它即可，不需要因为换成 V15 再安装一套 Basilisk。

```bash
cd /path/to/sat-platform-visual-composer-v15

python -m pip install --no-deps -e .
```

### Windows PowerShell

```powershell
cd D:\Project\sat-platform-visual-composer-v15
& D:\Project\old-sat\.venv\Scripts\Activate.ps1
python -m pip install --no-deps -e .
python -m sat_sim.agent_cli doctor --require-api --strict-assets
```

### 你要关注什么

如果 `doctor` 成功，继续下一步。

如果提示 Basilisk 不存在，可单独检查：

```bash
python scripts/ensure_basilisk_runtime.py --check-only
```

> 第一次使用不要急着处理所有高级能力。先让工作台启动并跑通一个 source-native/registered Capability。

### Linux

```bash
VENV_DIR=/path/to/original-sat/.venv ./scripts/start_local.sh
```

### Windows PowerShell

```text
http://127.0.0.1:8000/
```

## 4. 第一次不要自己搭，先用快速模板

在顶部找到：

```text
图形组装
```

进入后切换到：

```text
多模块装配 · V15
```

在“快速开始”区域选择：

```text
ADCS + Reaction Wheel · 可运行组合
```

### 你应该看到什么

画布上会出现一组 ADCS 模块，大致类似：

```text
Wheel Allocator ─────→ Rigid Body
       │
       ▼
Reaction Wheel ──────→ Saturation Monitor
```

其中 Reaction Wheel 是已经注册并通过接口兼容检查的模块。

此时先**不要手动改任何连接**。

---

## 5. 第一次运行

按顺序点击：

```text
校验装配
   ↓
生成 Python
   ↓
构建并运行
```

### 为什么要先校验

因为 V15 不允许“看起来连上了、实际类型不兼容”的模型直接执行。

它会检查：

- 信号数据类型；
- 端口所属模块；
- 单位；
- 时间语义；
- 模块接口；
- 允许的替换关系；
- feedback / solver 边界。

第一次使用时只需要记住：**校验通过再运行。**

---

## 6. 怎么判断运行成功

运行完成后，优先看执行状态：

```text
SUCCEEDED
```

然后点击：

```text
查看运行结果
```

进入“运行与结果”界面。

### 注意：SUCCEEDED 和 Validation 不是一回事

例如很短的 smoke run 可能出现：

```text
Execution: SUCCEEDED
Validation: INCONCLUSIVE
```

含义是：

- 仿真程序确实成功执行了；
- 但运行时间太短，不足以做某些工程验收判断。

所以不要看到 `INCONCLUSIVE` 就理解为程序崩溃。

---

## 7. 第一次看结果只看三处

进入“运行与结果”后，先只看：

1. **QoI / Metrics**：关键指标；
2. **Telemetry**：时间序列；
3. **Events / Validation**：异常、断言或验证结论。

其他 FMEA、traceability、artifacts 可以以后再学。

## 01｜先认识三个工作区

## 本课目标

理解 V15 的三个主要工作区，避免一开始就不知道“该在哪儿做什么”。

---

# 1. 图形组装：用来建模

这是你最常用的入口。

里面有两个模式。

## 1.1 任务流程

适合：

- 运行一个已有 Capability；
- 配置参数；
- 注入事件；
- 生成 Python；
- 执行任务。

它更像：

```text
模型
 ↓
参数
 ↓
事件
 ↓
输出
 ↓
代码
 ↓
运行
```

如果你只是“我要跑这个已有模型”，优先用任务流程。

## 1.2 多模块装配 · V15

适合：

- 类 Simulink 的模块化视图；
- 替换兼容模块；
- 看正式 signal binding；
- 加 Scope / Display / To Workspace；
- 做 baseline / replacement 对比。

它更像：

```text
模块 A ─signal─→ 模块 B
   │
   └──────────→ Scope
```

如果你的问题是“这些模块怎么组成一个模型”，优先用多模块装配。

---

# 2. 运行与结果：用来分析

这里负责完整结果，不负责建模。

你会在这里看：

- QoI / Metrics；
- Telemetry；
- Events；
- Validation；
- FMEA；
- Fault Traceability；
- Run Bundle artifacts；
- 数据下载；
- 报告。

记住一句话：

> **模型图保持干净，复杂结果去结果页。**

---

# 3. Scope / Display / To Workspace：局部观察

这三个东西虽然放在模型图上，但它们不是物理模块。

## Scope

用途：看曲线。

## Display

用途：看最近一次运行的末值。

## To Workspace

用途：把一条已记录 telemetry 导出 CSV / JSON。

三者都不会：

- 改变 TaskSpec；
- 改变 solver；
- 占用物理 fan-out；
- 进入生成的物理 Python。

---

# 4. 新手暂时不需要理解的词

你会在界面或文档中看到：

```text
Capability
TaskSpec
binding
simulation_ports
module contract
fingerprint
```

第一次使用可以先这样理解：

| 名词 | 新手理解 |
|---|---|
| Capability | 平台已经注册好的“可运行能力” |
| TaskSpec | 图形模型编译后的标准任务说明 |
| binding | 两个物理模块之间的正式信号连接 |
| simulation_ports | 模块允许输入/输出什么信号 |
| module contract | 什么模块允许替换什么位置 |
| fingerprint | 合同版本指纹，防止旧工程偷偷使用新语义 |

真正需要深入时再学习第 10 课。

---

# 5. 一个选择规则

以后不知道该去哪里时，按这个判断：

```text
我要搭模型/改参数？
  → 图形组装

我要看完整运行数据？
  → 运行与结果

我只想盯一两条局部信号？
  → Scope / Display

我要把模型交付给别人运行？
  → 导出可运行程序包
```

## 02｜第一个任务流程

## 本课目标

学习“任务流程”模式。它比多模块装配简单，适合先理解：

```text
一个 Capability
  → 参数
  → TaskSpec
  → Python
  → Run
```

---

# 1. 进入任务流程

打开：

```text
图形组装 → 任务流程
```

左侧可以搜索平台已注册的 Capability。

第一次建议选择一个简单部件，例如：

```text
component.reaction_wheel.v1
```

如果当前环境中该 Capability 没出现在列表，可以选择任意界面显示为可执行的部件/分系统 Capability。

---

# 2. 拖到画布

把 Capability 从左侧拖到画布。

然后使用：

```text
恢复基础流程
```

或：

```text
自动布线
```

典型流程会形成：

```text
模型
 ↓
参数配置
 ↓
事件注入
 ↓
输出选择
 ↓
Python 代码
 ↓
运行器
```

---

# 3. 点击节点看右侧属性

点击不同节点，观察右侧检查器。

第一次不要同时修改很多参数。

建议只修改一个容易理解的运行参数，例如：

```text
duration_s
```

修改以后，你应该看到当前模型被标记为需要重新编译/生成。

---

# 4. 校验图

点击：

```text
校验图
```

如果通过，说明：

- 图结构合法；
- Capability 一致；
- 类型化连接合法；
- 能编译为 Canonical TaskSpec。

如果失败，不要直接改 JSON，优先看画布错误提示。

---

# 5. 生成 Python

点击：

```text
生成 Python
```

右侧/代码区域会出现平台生成的确定性 Python。

这里最重要的认识是：

> 图形编辑器不是把节点名字随便拼成 Python；它先生成标准 TaskSpec，再由平台 exporter 生成代码。

所以生成代码是受注册执行边界保护的。

---

# 6. 只移动节点会不会让代码失效？

不会。

V15 中：

- 移动节点；
- 自动布局；
- 左对齐；
- 顶对齐；
- 等间距；

只改变画布坐标，不改变 TaskSpec。

真正会让代码变旧的是：

- 改参数；
- 改 Capability；
- 改物理连接；
- 改模块选择。

---

# 7. 构建并运行

点击：

```text
构建并运行
```

完成后进入：

```text
查看运行结果
```

---

# 8. 保存任务流程工程

你可以：

- 保存浏览器草稿；
- 加载浏览器草稿；
- 导出 `.satgraph.json`；
- 再导入 `.satgraph.json`。

推荐：重要模型不要只依赖浏览器草稿，额外导出 `.satgraph.json` 保存进 Git 或工程资料目录。

## 03｜ADCS + Reaction Wheel：第一次真正的模块装配

## 本课目标

完成一次最典型的类 Simulink 操作：

```text
加载 ADCS 父模型
  → 插入兼容 Reaction Wheel
  → 校验接口
  → 运行
  → 与 baseline 比较
```

---

# 1. 加载快速模板

进入：

```text
图形组装 → 多模块装配 · V15
```

选择：

```text
ADCS + Reaction Wheel · 可运行组合
```

这个模板的父 Capability 是：

```text
subsystem.adcs_fidelity.v1
```

它包含一个可替换的 `reaction_wheel` internal slot。

---

# 2. 看懂图，不需要先懂控制理论

你会看到类似：

```text
Wheel Allocator ─────→ Rigid Body
       │
       ▼
Reaction Wheel ──────→ Saturation Monitor
```

简单理解：

- Wheel Allocator：决定要给轮子多少控制力矩；
- Reaction Wheel：根据电机力矩推进轮速状态；
- Rigid Body：处理刚体姿态动力学；
- Saturation Monitor：检查轮速等状态是否超界。

---

# 3. 为什么 Reaction Wheel 能插进去

不是因为名字叫 Reaction Wheel。

平台会检查正式接口，例如：

```text
motor_torque_nm
   ↓
reaction wheel dynamics
   ↓
wheel_speed_rad_s
```

并检查：

- schema；
- dtype / shape；
- unit；
- timing；
- fan-in/fan-out；
- allow-list。

所以“拖得进去”意味着后端合同也认为它兼容。

---

# 4. 尝试恢复 baseline

在 Reaction Wheel 槽位中恢复：

```text
父适配器内部实现 / baseline
```

此时模型仍能运行，只是轮速推进使用父 Adapter 的内部实现。

然后重新选择：

```text
component.reaction_wheel.v1
```

你就完成了一次真实模块替换。

---

# 5. 校验和运行

依次执行：

```text
校验装配
生成 Python
构建并运行
```

运行摘要中应能看到类似：

```text
reaction_wheel_provider_capability_id
= component.reaction_wheel.v1
```

这比“节点颜色变了”更重要，因为它证明运行时真的切换了 provider。

---

# 6. 一键与 baseline 对比

点击：

```text
与基线对比
```

系统会自动：

1. 运行当前 replacement；
2. 恢复 baseline selection；
3. 运行 baseline；
4. 对共同 QoI 做差值。

第一次使用时重点看：

```text
qoi.adcs.final_pointing_error_deg
qoi.adcs.initial_pointing_error_deg
qoi.adcs.environment.total_torque_norm_nm
```

不要要求 replacement 一定“更好”；这里的目的首先是确认两种实现的物理结果是否一致、合理或存在预期差异。

---

# 7. 本课完成标准

- [ ] 能加载 ADCS + RW 快速模板；
- [ ] 能识别 Reaction Wheel slot；
- [ ] 能在 baseline 和 `component.reaction_wheel.v1` 间切换；
- [ ] replacement 运行后 provider ID 正确；
- [ ] 能完成一次 baseline comparison。

## 04｜整星电源 / 热控 / 轨道装配

## 本课目标

从单个 ADCS 子系统升级到多分系统耦合模型，学会使用整星快速模板和多个兼容模块。

---

# 1. 加载模板

进入：

```text
图形组装 → 多模块装配 · V15
```

选择：

```text
整星电源 / 热控 / 轨道 · 可运行组合
```

父 Capability：

```text
whole_spacecraft.power_thermal_orbit_coupled.v1
```

快速模板会自动匹配可运行组合，包括：

```text
orbit_environment.orbit_fidelity.v1
subsystem.eps.source_native.v1
subsystem.thermal.source_native.v1
```

---

# 2. 先用自动布局

点击：

```text
自动布局
```

V15 会根据正式 signal topology 排布物理模块。

对于 EPS ↔ Thermal 这种反馈关系，不会强行当成普通 DAG，而是按反馈拓扑处理。

---

# 3. 认识信号而不是盯模块名称

整星耦合中，你更应该关注“谁给谁什么数据”。

例如概念上可能包括：

```text
Orbit → shadow factor → EPS
Orbit → environment   → Thermal
EPS   → power/heat    → Thermal
Thermal → temperature feedback → EPS
```

具体端口名称以后端 `simulation_ports` 为准。

---

# 4. 模块库怎么用

左侧模块库可以：

- 搜索模块；
- 搜索 interface/domain；
- 只显示当前装配兼容模块；
- 拖到指定 slot；
- 拖到画布空白处，让系统自动找最近兼容 slot。

新手建议：**开启“仅兼容”筛选**，不要一开始看整个模块库。

---

# 5. 改运行参数

先只改三个常用参数：

```text
duration_s
step_s
sample_s
```

不要第一次就同时改大量物理参数。

改完点击：

```text
校验装配
```

---

# 6. 运行与结果

完成运行后，进入独立结果界面。

对于电源/热控/轨道模型，优先搜索：

- SOC / battery；
- power / margin；
- temperature；
- shadow；
- orbit/environment。

具体 telemetry 名称由当前 Capability 和 Run Bundle 决定。

---

# 7. 一个重要边界

V15 不是“任意 Basilisk class 自由拖拽器”。

你能拖入的模块必须：

```text
已经注册
+ 接口兼容
+ 当前父模型允许
+ 运行时有明确 owner
```

这也是为什么 V15 看起来像 Simulink，但不会允许完全无约束的连线。

## 05｜Scope / Display / To Workspace

## 本课目标

学习 V15 中正确的结果观察方式：

```text
完整分析 → 结果页
局部曲线 → Scope
局部末值 → Display
导出数据 → To Workspace
```

普通物理模块本身不画曲线。

---

# 1. Scope：看波形

以 ADCS + Reaction Wheel 为例。

## 操作步骤

1. 加载 `ADCS + Reaction Wheel · 可运行组合`；
2. 添加一个 `Scope`；
3. 点击 Reaction Wheel 的 output port；
4. 再点击 Scope 的 `signal` 输入；
5. 你会看到一条虚线 observer probe；
6. 构建并运行；
7. 选中 Scope；
8. 在右侧检查器选择解析到的 telemetry series。

例如 Reaction Wheel 的向量轮速输出可能解析为：

```text
adcs.rw.speed_rad_s_0
adcs.rw.speed_rad_s_1
adcs.rw.speed_rad_s_2
```

Scope 可以在这几个分量间切换。

---

# 2. Scope 为什么是虚线

因为它不是物理 binding。

Scope：

- 不进入 solver；
- 不改变 TaskSpec；
- 不占物理 fan-out；
- 不影响反馈环；
- 不进入生成的 runner。

所以可以放心给同一信号接多个观察器。

---

# 3. Display：看末值

如果你只想知道：

```text
最后 SOC 是多少？
最后温度是多少？
最后轮速是多少？
```

用 Display 比 Scope 更简单。

步骤：

1. 添加 Display；
2. 连接一个 output；
3. 运行；
4. 选中 Display；
5. 查看最近一次 Run 的末值。

Display 是单输入 observer。

---

# 4. To Workspace：导出 CSV / JSON

如果你需要用 MATLAB、Python、Excel 或其他分析程序处理数据，使用 To Workspace。

步骤：

1. 添加 To Workspace；
2. 接一个正式 output；
3. 完成一次运行；
4. 选中 To Workspace；
5. 选择 CSV 或 JSON 导出。

V15 会直接从 Run Bundle 的完整 telemetry 中读取数据，不依赖当前页面只预览了多少行。

---

# 5. 常见问题

## Q：Scope 没有曲线

先检查：

1. 是否已经完成一次 Run；
2. Scope 是否真的接在 output port；
3. 该 port 是否在 Run Bundle 中有 recorder/telemetry；
4. `sourceNode` 与 `sourcePort` 是否属于同一模块。

## Q：连接了 Scope 后模型结果变了吗？

正常情况下不会。Scope/Display/To Workspace 是 observer-only。

## Q：Scope 能实时刷新吗？

V15 当前是**运行后 Scope**，不是仿真步内实时 streaming scope。

## 06｜运行结果与故障定位

## 本课目标

学会判断“到底是程序没跑起来、验证没通过，还是物理结果不满意”。

---

# 1. 先区分三种状态

## 1.1 Execution / Run Status

最先看：

```text
SUCCEEDED
FAILED
CANCELLED
```

`SUCCEEDED` 表示执行程序完成。

## 1.2 Validation

可能出现：

```text
PASS
FAIL
INCONCLUSIVE
```

它是工程验证结论，不等于进程状态。

例如：

```text
Execution = SUCCEEDED
Validation = INCONCLUSIVE
```

通常表示运行成功，但时间窗或证据不足。

## 1.3 QoI / Metrics

这是“结果好不好”的工程指标。

即使运行成功，QoI 也可能不满足你的目标。

---

# 2. 结果页推荐查看顺序

新手按这个顺序：

```text
1. Execution status
2. Validation
3. QoI / Metrics
4. Telemetry
5. Events
6. Artifacts
7. FMEA / Traceability（有需要再看）
```

---

# 3. Telemetry 怎么看

不要一次打开几十条曲线。

先根据问题搜关键词：

ADCS：

```text
pointing
error
rw
speed
torque
```

EPS：

```text
soc
power
battery
margin
```

Thermal：

```text
temperature
thermal
heat
```

Orbit：

```text
orbit
shadow
environment
```

---

# 4. 运行失败时，画布有什么用

V15 保留**错误回标**，因为它属于建模诊断。

失败时优先：

1. 回到建模画布；
2. 查看红色/错误节点、端口或 binding；
3. 看工作台通知；
4. 再进入结果页看 Events / Validation；
5. 必要时进入 `runs/<run_id>/` 查看 Run Bundle。

---

# 5. 不要用 Scope 替代结果页

Scope 适合：

- 我只关心一条轮速；
- 我正在调一个控制器；
- 我想快速盯住局部状态。

结果页适合：

- 多变量分析；
- QoI；
- 事件；
- 验证；
- FMEA；
- 结果导出与归档。

## 07｜快速调参

## 本课目标

不手工反复“改参数 → 运行 → 记结果”，让 V15 自动跑少量候选并按一个 QoI 排序。

快速调参不是通用优化器，它适合工程上的小范围快速搜索。

---

# 1. 约束先记住

V15 快速调参当前限制：

- 1–3 个参数；
- 每参数 2–5 个候选；
- 总组合数最多 12；
- 参数必须是 Capability Schema 已注册的数值参数；
- 目标必须是已注册 QoI；
- 支持 minimize / maximize。

---

# 2. 用 ADCS 做第一个调参练习

加载：

```text
ADCS + Reaction Wheel · 可运行组合
```

打开：

```text
快速调参
```

选择目标：

```text
qoi.adcs.final_pointing_error_deg
```

方向：

```text
minimize
```

第一次只选一个参数，例如界面提供的：

```text
control_kp_nm_per_rad
```

候选值先用两个，例如：

```text
0.08
0.12
```

> 如果当前 Schema 给出的范围与示例不同，以界面 min/max 为准，不要强行输入越界值。

---

# 3. 启动扫描

系统会生成两个真实 Run，而不是在浏览器里算一个公式。

完成后会给出排名，例如：

```text
Candidate A  → final pointing error = ...
Candidate B  → final pointing error = ...
Best         → ...
```

---

# 4. “调参最优”是什么意思

扫描完成后，最佳 Run 可以作为结果参考，但当前模型参数还没有自动改变。

因此 V15 会把它标成：

```text
调参最优
```

而不是假装它就是当前模型。

---

# 5. 真正应用最优参数

确认结果后点击：

```text
应用最优参数
```

此时：

- 参数写回当前模型；
- 旧 TaskSpec 变 stale；
- 旧生成代码变 stale；
- 需要重新生成 Python / 构建运行。

这是正确行为，因为模型语义真的变了。

---

# 6. 什么时候不要用快速调参

不适合：

- 几十个参数；
- 大规模全局优化；
- 每个 Run 很昂贵；
- 需要贝叶斯优化/TPE 等专业搜索算法。

V15 这个入口的定位是：**小规模、可解释、快速工程比较。**

## 本课目标

# 1. 多选和框选

```text
空白区域拖动                框选
Ctrl/Cmd + A                全选
```

选中多个对象后拖其中一个，可以整体移动。

# 2. 自动布局和对齐

工具栏：

```text
自动布局
左对齐
顶对齐
水平等间距
垂直等间距
```

纯布局不会导致生成 Python 过期。

```text
方向键             20 px
Shift + 方向键      5 px
```

---

# 4. 复制粘贴为什么只允许观察器

V15 允许：

```text
Ctrl/Cmd + C
Ctrl/Cmd + V
Ctrl/Cmd + D
```

复制：

- Scope；
- Display；
- To Workspace。

不允许随意复制物理 slot，例如 EPS、Thermal、Reaction Wheel。

原因是物理模块由父 Capability 合同唯一约束；随意复制会生成没有定义的拓扑。

# 5. 撤销 / 重做

```text
Ctrl/Cmd + Z
Ctrl/Cmd + Shift + Z
Ctrl/Cmd + Y
```

# 6. 怎么保存工程

建议区分三种东西。

## 6.1 浏览器草稿

适合临时继续工作。

缺点：不适合作为正式工程归档。

## 6.2 `.satgraph.json`

适合保存可编辑图形工程。

建议：重要模型必须导出并放进版本管理。

## 6.3 可运行程序包 ZIP

适合交付和复现运行。

它包含 TaskSpec、图工程、runner、启动脚本和 manifest。

建议提交：

```text
项目文档
```

通常不要提交大量：

```text
runs/
.sat_sim_api/
__pycache__/
临时缓存
```

是否提交完整 Run Bundle 取决于你的试验归档规范。

## 09｜导出可运行程序包

## 本课目标

把“只能在网页里运行的图”变成一个别人可以拿走的 Python 项目。

---

# 1. 先确保当前模型是你要交付的版本

建议按顺序：

```text
校验
  ↓
生成 Python
  ↓
构建并运行一次
  ↓
确认结果
  ↓
导出可运行程序包
```

---

# 2. 导出的 ZIP 里有什么

典型内容：

```text
my_simulation_program/
├── run_simulation.py
├── task_spec.json
├── visual_graph.json 或 assembly_graph.json
├── program_manifest.json
├── run.sh
├── run.bat
└── README.md
```

### 这些文件分别是什么

`run_simulation.py`  
实际运行入口。

`task_spec.json`  
模型编译后的标准任务描述。

`assembly_graph.json` / `visual_graph.json`  
图形工程信息。

`program_manifest.json`  
程序包元数据、合同 fingerprint、module selection 等。

`run.sh` / `run.bat`  
启动脚本。

---

# 3. 怎么运行导出的程序包

导出包**不包含整个 Python/Basilisk runtime**。

所以要在已经安装匹配 SAT 环境的机器上运行。

Linux/macOS：

```bash
bash run.sh
```

Windows：

```bat
run.bat
```

通用方式：

```bash
python run_simulation.py
```

---

# 4. 为什么推荐 `bash run.sh`，而不是 `./run.sh`

ZIP 解压工具不一定可靠保留 Unix executable bit。

所以：

```bash
bash run.sh
```

跨解压工具更稳。

---

# 5. Scope 会不会进入交付程序？

Scope/Display/To Workspace 工程信息会保存在图工程中，方便以后重新打开。

但它们：

```text
observer_runtime_effect = none
```

不会进入物理 runner，也不会改变 TaskSpec。

---

# 6. 推荐交付内容

正式交付一个仿真任务时，建议至少保存：

```text
程序包 ZIP
V15 版本/commit
运行环境 Python 版本
依赖锁文件/可用 wheelhouse
代表性 Run ID 或 Run Bundle
验收结果说明
```

## 10｜理解 TaskSpec 与生成代码

## 本课目标

在已经会用以后，再理解 V15 为什么不是一个“拖节点拼 Python”的玩具编辑器。

---

# 1. 真正的编译链

V15 的核心链路是：

```text
图形工程
  ↓
端口/模块合同校验
  ↓
Canonical TaskSpec
  ↓
Execution Plan
  ↓
Deterministic Script Exporter
  ↓
run_simulation.py
  ↓
Registered Capability Adapter
```

---

# 2. TaskSpec 是什么

TaskSpec 可以理解为：

> 与 UI 无关、与节点坐标无关的标准任务说明书。

所以：

```text
节点从左边拖到右边
```

不应该改变 TaskSpec。

而：

```text
Kp 从 0.08 改成 0.12
```

应该改变 TaskSpec。

这也是 V15 为什么能够正确判断“代码是否 stale”。

---

# 3. 为什么不能放任意 Python Block

如果允许任意节点直接执行任意 Python：

- 类型检查会失效；
- module contract 会失效；
- 生成程序无法稳定复现；
- 图上审核内容与实际执行代码可能不一致；
- 安全边界无法保证。

因此 V15 只允许注册能力和注册模块进入物理执行链。

---

# 4. module replacement 为什么有 fingerprint

端口合同或模块接口升级以后，旧工程不能默默继续使用新语义。

fingerprint 用于发现：

```text
这个图是按旧接口创建的
但现在模块合同已经变了
```

这时应该重新加载/保存/审核，而不是偷偷运行。

---

# 5. 什么时候需要读 TaskSpec

日常建模不需要。

建议在以下场景读取：

- 调试平台行为；
- 做自动化测试；
- 接入其他系统；
- 审计生成程序；
- 比较两个图为什么生成不同代码。


---

## 11｜与其他前端或项目集成

## 本课目标

解释“我的另一个项目需要前端/仿真能力，怎么和 V15 打通”。

不要一开始复制 V15 的前端源码。优先把 SAT 当成一个**独立仿真后端/执行服务**。

---

# 1. 推荐的三种集成方式

## 方式 A：直接使用 V15 工作台

适合：

- 内部工程师；
- 仿真建模；
- 调试；
- 研究和验证。

你的其他项目只需要链接/打开 V15 工作台，不需要重复开发 Visual Composer。

这是成本最低的方式。

---

## 方式 B：其他系统调用导出的程序包

适合：

- Agent；
- 批处理平台；
- CI；
- 后台作业；
- 不需要网页编辑器的业务系统。

流程：

```text
V15 里把模型搭好
  ↓
导出可运行程序包
  ↓
其他系统调用 run_simulation.py
  ↓
读取 Run Bundle / stdout / artifacts
```

这是最容易稳定落地的集成方式。

---

## 方式 C：你的前端直接调用 SAT REST API

适合：

- 需要自定义业务 UI；
- 需要把仿真嵌到已有 Web 项目；
- 不想使用 V15 原生工作台界面。

SAT 启动后默认：

```text
http://127.0.0.1:8000
```

先测试：

```bash
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/capabilities
```

Visual Composer 相关 API 包括：

```text
GET  /visual-composer/assemblies
GET  /visual-composer/assemblies/{capability_id}
GET  /visual-composer/simulation-ports/{capability_id}
GET  /visual-composer/module-replacements/{capability_id}
GET  /visual-composer/module-library
POST /tasks/compile-graph
POST /tasks/compile-assembly
POST /tasks/export-script
POST /tasks/export-assembly-script
POST /tasks/export-program
POST /runs
POST /runs/{run_id}/execute-async
GET  /runs/{run_id}/execution
GET  /runs/{run_id}/metrics
GET  /runs/{run_id}/telemetry
```

---

# 2. 前端项目不要直接跨域硬连

如果你的 React/Vue/Next/Vite 开发服务器运行在另外一个端口，浏览器会涉及同源/CORS 问题。

V15 当前不建议依赖“所有来源都开放 CORS”。

更稳的方式是：

```text
浏览器
  ↓
你的前端 dev/prod server
  ↓ 反向代理 /sat-api/*
SAT :8000
```

例如开发环境让前端服务器把：

```text
/sat-api/health
```

代理到：

```text
http://127.0.0.1:8000/health
```

生产环境则让 Nginx/网关统一做同源路由。

---

# 3. 最小前端连通测试

前端只先实现健康检查，不要上来就重写整个 Visual Composer：

```javascript
const res = await fetch('/sat-api/health');
if (!res.ok) throw new Error('SAT backend unavailable');
const health = await res.json();
console.log(health);
```

然后再获取 Capability：

```javascript
const res = await fetch('/sat-api/capabilities');
const capabilities = await res.json();
console.log(capabilities);
```

当这两步稳定以后，再接任务编译/运行。

---

# 4. 推荐的业务集成层次

不要让业务前端理解所有 TaskSpec 细节。

推荐：

```text
业务前端
   ↓ 简化业务请求
你的业务后端 / BFF
   ↓ SAT API
SAT V15
   ↓
Run Bundle
```

BFF 负责把“用户业务输入”转换为平台需要的 Capability / TaskSpec / template 选择。

这样以后 V15 内部合同升级，不需要让所有页面跟着改。

---

# 5. 如果你的项目只是“需要一个仿真功能”

优先顺序：

```text
1. 导出程序包调用
2. 服务端 REST API 调用
3. 复用 V15 原生工作台
4. 最后才考虑复制/修改 V15 前端源码
```

通常不要直接 fork 前端然后把所有 SAT 内部状态管理搬进业务项目。

## 12｜常见问题与排查清单

## 1. 浏览器打不开 127.0.0.1:8000

检查启动终端是否还在运行。

再执行：

```bash
curl http://127.0.0.1:8000/health
```

如果 curl 也失败，问题在服务启动，不在浏览器。

---

## 2. doctor 失败

执行：

```bash
python -m sat_sim.agent_cli doctor --require-api --strict-assets
```

根据提示检查：

- 当前 Python 是否来自正确 `.venv`；
- editable install 是否指向 V15；
- 依赖是否安装；
- 资产是否缺失。

---

## 3. Basilisk 不存在

检查：

```bash
python scripts/ensure_basilisk_runtime.py --check-only
```

如果你有 wheel：

```bash
python scripts/ensure_basilisk_runtime.py --wheel /path/to/bsk-2.11.0.whl
```

注意：不是所有 source-native Capability 都必须依赖 Basilisk，但 Basilisk 专项能力需要它。

---

## 4. 模块拖不上去

常见原因：

- interface 不兼容；
- payload schema 不兼容；
- unit 不兼容；
- timing 不兼容；
- allow-list 不允许；
- 这个 slot 不是 replaceable；
- 父模型不拥有该运行时 slot。

先打开“仅兼容模块”筛选。

---

## 5. 端口连不上

检查：

- output → input 方向；
- 数据类型；
- source/target port 所属模块；
- fan-in/fan-out；
- binding 是否已经存在；
- feedback policy。

不要通过手改 JSON 强行绕过校验。

---

## 6. 生成 Python 按钮提示代码过期

如果你修改了：

- 参数；
- 模块选择；
- 物理连接；

这是正常的，需要重新生成。

如果只是移动/对齐节点，V15 不应该令代码过期。

---

## 7. Scope 没有数据

检查：

1. 是否完成过一次 Run；
2. probe 是否接 output；
3. 该信号是否被 recorder 记录；
4. sourceNode/sourcePort 是否匹配；
5. Run Bundle 中是否存在对应 telemetry。

---

## 8. To Workspace 导不出

只有 `To Workspace` observer 能调用数据导出。

并且必须：

- 已完成一次运行；
- observer 已接合法 output；
- 该 output 已解析到 telemetry。

---

## 9. Run 是 SUCCEEDED，但 Validation 是 INCONCLUSIVE

这通常不是程序失败。

可能是：

- 仿真时长过短；
- 验证窗口不足；
- 某项判据没有足够证据。

先看 Execution，再看 Validation 原因。

---

## 10. 导出的程序包在另一台机器跑不了

程序包不包含整个 runtime。

另一台机器仍需：

- 合适的 Python；
- SAT 包；
- 需要的依赖；
- Basilisk（如果该 Capability 需要）。

---

## 11. Windows 下 run.sh Permission / 无法执行

Windows 使用：

```bat
run.bat
```

Linux/macOS 推荐：

```bash
bash run.sh
```

不要依赖 ZIP 解压后保留 executable bit。

---

## 12. 不知道问题在哪时的固定排查顺序

```text
1. doctor
2. /health
3. 画布校验
4. Execution status
5. Validation / Events
6. telemetry 是否存在
7. Run Bundle artifacts
8. 对应专项 pytest
```

推荐专项测试：

```bash
pytest -q \
  tests/test_visual_graph.py \
  tests/test_assembly_graph.py \
  tests/test_visual_diagnostics.py \
  tests/test_visual_results.py \
  tests/test_visual_tuning.py \
  tests/test_web_workbench.py
```
