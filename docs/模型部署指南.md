# 仿真 Agent 模型与硬件部署说明

## 1. 部署目标

平台采用“本地完整可用、服务器按需增强”的结构。TaskSpec 校验、能力解析、计划、执行、验证和报告均可在本地不调用大模型完成。

## 2. 任务分级

| 等级 | 工作 | 推荐位置 |
|---|---|---|
| L0 | 表单、YAML、Patch、Schema、计划、执行、报告 | 笔记本/CPU |
| L1 | 简单自然语言、单字段修改 | 本地模板或小模型 |
| L2 | 长需求、多分系统、多事件语义解析 | 服务器模型 |

服务器不可用时必须显式产生 `REMOTE_MODEL_UNAVAILABLE_FALLBACK`，不得静默假装使用了远程模型。

## 3. 支持后端

- `template`：确定性模板，正式基线；
- `command`：框架无关的 stdin/stdout 模型进程；
- `openai` / `deepseek`；
- `openai_compatible` / `qwen` / `vllm`。

Qwen/vLLM 示例：

```bash
sat-agent parse "建立整星功率热轨联合仿真" \
  --backend vllm \
  --model <model-name> \
  --model-base-url http://server:8000/v1
```

## 4. 硬件建议

- RTX 5060：适合 7B～8B 量化模型和本地开发；
- 4×96 GB GPU 服务器：适合 32B/70B、批量 Provider 评测和后续 LoRA；
- Basilisk/Python 单次仿真主要使用 CPU，GPU 不会自动加速物理模型；
- 服务器应作为可上下线 Worker，不应成为表单和确定性仿真的硬依赖。

## 5. Provider-specific 评测

既有工程版本 的正式 140×5 基线使用确定性本地/模板路径，并在首轮执行 7 个登记 Runner 案例。接入真实 Qwen、DeepSeek 或其他服务后，必须在同一 Manifest 上单独生成 Provider 报告，至少统计：

- TaskSpec/Plan 一致性；
- false accept/reject；
- 路由和 Claim 翻转；
- 超时、限流和结构化输出失败；
- 本地降级是否显式记录。

模型版本、提示词版本、温度、上下文和知识库快照必须进入评测元数据。

## 6. RAG 边界

RAG 可检索文档、示例和参数解释，但不能决定 capability support、owner、runner、native/proxy、参数等级、Claim 或运行时注入真值。
