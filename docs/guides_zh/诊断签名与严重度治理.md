# 诊断签名与严重度治理

## 1. 目的

本治理将“仿真物理验证”和“诊断可学习性验证”拆分为两道独立技术门。物理门确认故障机制被正确注入；诊断门确认故障/名义配对遥测中存在受治理、可复现的诊断特征。

## 2. 诊断签名库

首批签名覆盖：

- `ADCS_RW_FRICTION_INCREASE`
- `ADCS_RW_JAM`
- `ADCS_RW_TORQUE_AUTHORITY_LOSS`

每份签名声明必需通道、确定性指标、阈值、权重、最低诊断得分和阈值冻结条件。初始阈值均标记为 `provisional_until_basilisk_18_case`，不得解释为飞行标定阈值。

## 3. 严重度模型

严重度必须绑定实际改变的仿真参数：

- 摩擦增加：`drag_nms` 随归一化严重度增加；
- 力矩权限下降：`torque_scale` 随归一化严重度下降；
- 反作用轮卡死：当前底层机制为二值完全卡死，严重度固定为 `1.0/critical`。

不得为二值卡死生成虚假的连续严重度标签。

## 4. 资格边界

代理数据可以验证合同和规则实现，但只能得到 `REVIEW`；只有 A 级 Basilisk Pair 才能形成诊断候选。诊断候选仍不能直接训练，必须经过签名冻结和 Pair 级专家审核。

## 5. 目标泄漏防护

诊断证据被分为：

- `observable_telemetry`：可作为模型输入；
- `operational_estimate`：只有在真实系统能够产生同类估计时才可作为模型输入；
- `simulator_truth`：仅用于物理验证，不能计入诊断得分。

当前数据合同明确禁止将 `status.adcs.rw.available_0`、`estimate.adcs.rw.effective_max_torque_nm_0` 和直接故障注入生成的摩擦真值作为 AstroGraph 数据驱动模型输入。它们只能用于物理证据和审核。
