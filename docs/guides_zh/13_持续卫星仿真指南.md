# 持续卫星仿真（Continuous Satellite Simulation）

## 适用范围与实施状态

在 V15 原有软实时交互会话上增加 opt-in 的 `continuous: true`。
当前只对 `whole_spacecraft.unified_native.v1` 启用；原有批处理模式、有限时长会话和分系统独立调试保持不变。
这是基于 **同一个 Basilisk 实例的连续状态推进**，不是 CSV/遥测循环回放，也不是硬实时/HIL。

持续模式不会因为 `simulation.duration_s`、`max_sim_time_s`、`max_wall_time_s` 或 `idle_timeout_s` 达到原先的上限而结束；
只有明确 `stop`/`abort`、仿真异常、服务关闭或底层物理/时间表示限制才能终止。
`simulation.duration_s` 仍用于初始模型/热控配置（必须正数），**不是持续模式的结束时刻**。
现实计算机不可能保证物理意义上的无期限可靠运行；连续服务仍须进行长稳测试和重启恢复设计。

## 使用方法

1. 安装与仓库要求匹配的 Basilisk、FastAPI 等依赖。
2. 设置环境变量 `SAT_SIM_INTERACTIVE_ENABLED=1` 并按 `README.md` 启动。
3. 在 Web 工作台「实时会话」中选择「整星」并勾选「持续运行（手动停止）」。
4. 选择仿真推进量子、1× 墙钟节拍后创建并启动会话。
5. 通过遥控面板发送已注册命令；在遥测面板或 WebSocket 中订阅已批准的流。
6. 如需归档，发送 `stop`；如需强制放弃，发送 `abort`。

REST 创建请求示意：

```json
{
  "session_id": "satellite-1",
  "capability_id": "whole_spacecraft.unified_native.v1",
  "continuous": true,
  "quantum_s": 0.5,
  "rate": 1.0,
  "paced": true,
  "task_spec": {
    "simulation": {"duration_s": 60, "sample_s": 0.5, "solver": {"step_s": 0.2}},
    "parameters": {"values": {}},
    "outputs": {"telemetry_streams": [
      {"stream_id": "whole.fast", "sample_s": 0.5, "fields": ["orbit.radius_m"]}
    ]}
  }
}
```

控制端点：`POST /interactive/sessions/satellite-1/control`，请求 `{"action":"start"}`、`{"action":"pause"}`、`{"action":"resume"}`、`{"action":"stop"}` 等。
遥控端点：`POST /interactive/sessions/satellite-1/commands`。
遥测端点：`WS /interactive/sessions/satellite-1/telemetry`。
遥控需要 `session_revision` 和授权角色，严格遵循 `configs/interactive/realtime_capability_matrix.json`。

## 工程边界与后续验收

- 持续模式保持相同 Basilisk 状态，不按预先生成的数据集循环播放。
- 运行时记录器分段清空，连续执行的停止时间只保留末次值；软实时漂移历史保留最近 4096 个采样，但总计数与最大漂移仍保留。
- 遥测总线使用有限环形缓冲，慢消费者会收到 GAP；持久工作区仍连续写盘，**当前没有按日轮转/限额策略**。
- 持续模式的 ACK 和会话事件只保留最近 4096 条内存缓存，序号仍单调增长；完整 ACK/事件继续写入哈希链日志。指定 command_id 的 ACK 查询在有工作区时会遍历日志读取完整历史，未指定 command_id 时返回内存窗口。
- 持续模式的命令 ID 幂等索引保存在 SQLite `command_ids.sqlite`，不会通过淘汰老 ID 来允许重复执行；无显式工作区时使用临时磁盘索引，会话退出即销毁。
- `finalize_telemetry()` 以流式方式校验哈希链、分流写出 JSONL 与计算 SHA-256，归档阶段不再把所有遥测帧保留在 Python 内存中；原有 manifest v1 保持兼容。
- 当前 **尚未完成** 原始遥测日志按日轮转/配额与 Run Bundle 封存全过程流式化：`seal_interactive_workspace()` 仍会完整载入历史 trace。真正 7×24 服务需继续拆分封存与按段归档，防止停止后内存或磁盘耗尽。
- 服务进程重启不等于恢复完整 Basilisk 状态；目前是命令重放/工作区校验方向，完整检查点恢复尚未实现。
- 尚不能以短测试声明 24 小时、7 天或 30 天无故障运行。

推荐测试：
```bash
pytest -q tests/interactive/test_continuous_session.py
pytest -q tests/interactive/test_unified_segmented_execution.py tests/interactive/test_interactive_api.py
python scripts/run_interactive_performance_benchmark.py --profile formal
```

验收应覆盖遥控闭环、连续遥测、Basilisk 跨初始时长、数值等价、进程资源曲线、断线续读，以及 24 小时真实墙钟稳定性。

## 停止与封存状态

- `SessionSnapshot.state=COMPLETED` 表示物理仿真正常结束，不自动表示证据已验证封存。
- `archive_status` 在工作区存在时从 `NOT_READY` 转为 `SEALING`，成功后为 `SEALED`，异常则为 `FAILED` 并给出 `archive_error`；`ABORTED` 等无需封存的结束状态标为 `NOT_APPLICABLE`。
- 实时会话界面独立显示归档状态，避免运行完成但 Run Bundle 不存在的误判。长期运行的分段封存及磁盘配额仍是后续工作。

## 长时间戳加速回归

GitHub 原生测试除了短时 180 s 场景，还包含 3600 s **仿真时间**的加速运行，量子 0.5 s，覆盖连续状态推进、动态遥控、原生采样、工作区哈希链及终态封存；依然不等于真实墙钟 3600 s。测试命令：

```bash
SAT_SIM_CONTINUOUS_SOAK_TARGET_S=3600 pytest -q -s tests/interactive/test_continuous_soak.py
```

24 h 真实墙钟及项目专用 `bsk==2.11.0+satfix1` 的长期门仍需独立验收。

## 内存中的遥测环形缓存

- 持续整星的 `runtime.trace` 包含大量原生模型字段，不开放给普通 API 客户端；该内部流仅缓存最近 **256 帧**供诊断，其完整记录仍由工作区 `telemetry.jsonl` 哈希链落盘。
- 白名单流（如 `whole.fast`、`adcs.fast`）依旧按 `telemetry_buffer_frames` 的容量限制保存最近数据，WebSocket 断线续读和 GAP 语义保持不变。
- 这降低的是 **内存回放缓存** 的成本，不构成物理运行内存泄漏已经排除的证明；还需比较不同仿真时长的进程 RSS 与 Basilisk 内部对象规模。

## 连续遥测存储容量保护

- `telemetry_log_max_bytes` 默认 `0`（不限制单会话原始 `telemetry.jsonl` 的字节数）；设置正整数后，每次实际写盘前精确检查预计字节数，超限抛出 `TELEMETRY_LOG_BUDGET_EXCEEDED`。这是 **主日志预算**，不是对工作区全部文件的配额。
- `telemetry_min_free_disk_bytes` 默认 67108864（64 MiB）；持续模式每 128 个遥测帧检查一次工作区所属磁盘的剩余空间，低于预留量抛出 `TELEMETRY_DISK_RESERVE_EXHAUSTED`。可以设为 `0` 关闭此保护，但不建议生产环境关闭。
- 两项防护只对持续会话生效；故障会终止会话，并通过 `SessionSnapshot.terminal_error` 显示原因。先前完成写盘的证据仍按原哈希链保存，不会自动删旧数据或循环覆盖。
- 这不能替代按段轮转、备份、日志压缩、异地存储或进程状态恢复；归档仍可能额外占用与原始遥测数据相近甚至更多的磁盘空间。

## 持续会话的流式 Run Bundle 封存

- 持续会话与有限时长会话使用不同的封存执行路径，生成的 Run Bundle v1 文件结构及 `semantic_trace_sha256` 保持兼容。
- 持续会话的 `runtime.trace` 逐条读入和计算 SHA-256，`semantic_trace.json` 逐条流式写出，不再构建全量 Python `list[dict]`。完整遥测原始哈希链仍由工作区保存。
- HF-8 工程物理门禁采用流式统计：保持燃料单调性、指向误差首/末/极小值以及逐点物理边界检查；为避免无上限内存积累，物理异常详情达到 2048 条时拒绝封存（`CONTINUOUS_PHYSICAL_ISSUE_LIMIT_EXCEEDED`）。该上限不代表额外的物理真实性认证。
- 遥控效果时间窗按时间顺序扫描遥测，持有的数据规模与已确认的遥控命令数量成正比，而不与遥测总帧数成正比。
- Run Bundle 文件 SHA-256 改为 1 MiB 分块计算。**目前仍会完整加载遥控指令事件以生成效果窗口**；超长会话还需要分段归档、分段封存和完整遥控事件的流式索引设计。
- 该改造不意味着已经实现 Basilisk 物理状态的 checkpoint/restart；重启后的严格物理状态连续性仍未验收。

## 封存的原子发布与失败处理

- 持续会话先在工作区的 `.run_bundle.pending/` 生成语义轨迹、校验结果与 Run Bundle 元数据。只有在完整生成并通过文件哈希验证后，才将其重命名为正式 `run_bundle/`。
- 如果封存过程发生异常，**正式 `run_bundle/` 不会出现未验证的半成品**；未完成的暂存目录原样保留供检查。再次封存时若发现遗留暂存目录，明确报错 `INTERACTIVE_PARTIAL_STAGING_EXISTS`，不会覆盖证据或自动删除。
- 当前暂无自动修复失败暂存目录的能力，检查并恢复前不得将 `archive_status=FAILED` 认定为归档成功。该防护不是操作系统崩溃后已落盘文件必然持久化的保证，生产部署仍需考虑文件系统同步策略。

## 连续遥测原始日志分段轮转

- `telemetry_segment_max_bytes` 默认 67108864（64 MiB），仅持续会话生效；`0` 可关闭轮转。单帧超过分段容量会明确失败（`TELEMETRY_FRAME_EXCEEDS_SEGMENT_CAP`），不会截断帧内容。
- 达到阈值时，将当前 `telemetry.jsonl` 原子重命名为 `telemetry_segments/segment-00000001.jsonl` 等已关闭分段，新的 `telemetry.jsonl` 继续接收后续遥测；已关闭分段的 SHA-256 与字节数记录在 `telemetry_segments/index.json` 中。全局遥测事件序号和 `previous_hash` 不会因分段而重置。
- 工作区的完整性检查按编号检索分段和活动文件，逐段校验内容 SHA-256、跨段哈希链与连续序号；索引缺失、分段缺失或篡改时，拒绝验收。异常轮转遗留未登记分段时要求人工处理，不自动删除或跳过。
- 停止后的 `telemetry_manifest.json` 记录逻辑上完整拼接数据流的 SHA-256 与来源分段信息；流式 Run Bundle 封存会把已关闭分段及活动文件拼接成兼容旧版的 `interactive/telemetry.jsonl`。
- `telemetry_log_max_bytes` 对本会话全部已关闭分段与活动日志的合计字节数生效。**分段轮转并不释放磁盘空间**，不是无限存储，也不取代总量配额与离线归档。当前仍需完成真正的分段压缩/外部归档与保留期清理机制，且不能无验证地删除旧段。
